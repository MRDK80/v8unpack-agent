# AGENTS.md

Точка входа для AI coding agents и автоматизации, работающих с этим
репозиторием. Документ объясняет, как исследовать, менять и проверять проект.
Он не заменяет [README.md](README.md), [CONTRIBUTING.md](CONTRIBUTING.md) и
документы из [docs/](docs/): при расхождении верны они и фактический код.

## Назначение и граница ответственности

`v8unpack-agent` — Python-библиотека и CLI над upstream-распаковщиком
`v8unpack`. Вход — каталог уже выполненной и распакованной выгрузки
конфигурации 1С. Выход — опись форм, текстовый слой, индексы модулей,
контекст для LLM и отчёт о запуске.

Пакет не распаковывает контейнер сам, не подключается к живой
информационной базе и не читает её данные. Граница ответственности
компонентов — в разделе «Кто что решает» [README.md](README.md).

## Публичные контракты

- **Library API** — модули и имена из раздела «Публичная поверхность»
  [README.md](README.md); у каждого модуля есть канонический документ в
  `docs/`. Часть возможностей существует только как library API и в CLI не
  встроена: например, `FormRagIndex` и `FormDispatcher`
  ([docs/form_rag.md](docs/form_rag.md)).
- **CLI** — две точки входа, перечисленные ниже. Машиночитаемый каталог
  команд, параметров и кодов выхода — `v8unpack-agent-run --describe-cli`
  ([docs/cli_introspection.md](docs/cli_introspection.md)); флаги сверяйте с
  ним или с `--help` текущей версии, а не с этим файлом.

Отсутствующие возможности не заявляются и не используются: MCP-сервер,
hosted service, FastAPI-сервис, адаптеры LangChain/LlamaIndex, функции
`index_cf()` и `rag.rebuild()`.

## CLI-команды и коды выхода

### `v8unpack-agent-run`

Console script из `[project.scripts]` в `pyproject.toml`; без установки —
`python -m v8unpack_agent.cli`.

```bash
v8unpack-agent-run --help
v8unpack-agent-run EXPORT_ROOT --report-path post-run.json
```

`--report-path` обязателен, каталог-родитель должен существовать.
Коды выхода — константы `EXIT_*` в `v8unpack_agent/cli.py`:

| Код | Значение |
|---:|---|
| 0 | все объекты обработаны полностью |
| 2 | ошибка аргументов или корень не является каталогом |
| 3 | degraded: есть частичные или отказавшие объекты |
| 4 | управляемая фатальная ошибка пайплайна |
| 5 | ошибка записи отчёта |
| 6 | фатальная ошибка и ошибка записи одновременно |

Degraded (3) — неуспешное завершение, а не «почти успех». Подробности —
[docs/runner.md](docs/runner.md) и [docs/run_report.md](docs/run_report.md).

### `python -m v8unpack_agent.search_cli`

Opt-in общий поиск, подкоманды `build` и `query`; console script не
объявлен.

```bash
python -m v8unpack_agent.search_cli --help
python -m v8unpack_agent.search_cli build --help
python -m v8unpack_agent.search_cli query --help
```

Коды выхода 0, 2, 3, 4, 5 используют те же константы `cli.py`; кода 6 у
поиска нет. Условия каждого кода — [docs/search_cli.md](docs/search_cli.md).

## stdout, stderr и артефакты запуска

- `v8unpack-agent-run`: stdout — краткая человекочитаемая сводка без путей и
  доменных данных; с флагом `--json` — один JSON-объект envelope
  `schema_version` 1.0 ([docs/cli_json.md](docs/cli_json.md)). Полный
  результат — JSON-отчёт по `--report-path`
  ([docs/run_report.md](docs/run_report.md)). Сообщения об ошибках — в stderr.
- `search_cli`: stdout — один канонический JSON схемы `search_cli/1`; при
  ошибке аргументов JSON не выводится. stderr — однострочные
  санитизированные сообщения без traceback. `build` пишет снимок по
  `--snapshot` (и `--object-snapshot`, если задан); `--cache-dir` —
  каталог возобновляемого кэша векторов.
- Стандартные потоки переводятся в UTF-8.
- Новые артефакты запуска описываются в документации команды вместе с
  изменением поведения.

## Окружение разработки

Требуется Python 3.10 или новее. Из корня клона:

```bash
python -m pip install -e ".[test,dev]"
```

Extra `test` — `pytest` и `numpy`, `dev` — запиненные `ruff` и `mypy`.
Extras `fast` и `local-model` нужны только для смыслового поиска; веса
локальной модели не скачиваются, сеть не используется.

## Local gate

Перед публикацией изменения кода или документации, из корня клона:

```bash
ruff check .
mypy
python -m pytest -q
```

- Все три команды должны завершиться с RC=0 на одном и том же финальном
  коммите.
- `mypy` запускается без аргументов: область задана `[tool.mypy] files` в
  `pyproject.toml` (`v8unpack_agent` и `examples`); явные аргументы её
  переопределяют.
- Версии `ruff` и `mypy` запинены в extra `dev`; набор правил ruff — дефолт
  запиненной версии, конфигурация линтеров только в `pyproject.toml`.
- Pre-commit hooks и secret-baseline в репозитории не настроены; не ссылайтесь
  на них как на проверки.

## Поддерживаемые Python и ОС

`requires-python = ">=3.10"`. CI (`.github/workflows/tests.yml`) проверяет:

- `pytest` — Ubuntu и Windows × Python 3.10 и 3.12;
- `lint / ruff + mypy` — Ubuntu и Windows, Python 3.12.

Шесть обязательных jobs должны быть успешны на точном проверяемом SHA.
Локальная проверка на одной ОС не заменяет Windows CI.

## Обезличенность

В коде, тестах, примерах, документации, отчётах и логах запрещены:

- имена рабочих баз, хостов, IP-адреса, строки подключения;
- абсолютные и домашние пути, имена пользователей и организаций;
- фрагменты реального кода и метаданных конфигураций.

Тесты используют синтетические деревья во временных каталогах и
заглушку-распаковщик. Перед публикацией просмотрите весь diff, включая новые
файлы.

## Кроссплатформенные правила

- Пути строятся через `pathlib` (или `os.path.join`); литеральные
  разделители пути Windows и абсолютные пути в коде и тестах не используются.
- Текст читается и пишется с явным `encoding="utf-8"`.
- Байтовые фикстуры, чьи размер или хеш проверяются, создаются через
  `write_bytes`, чтобы перевод строк не зависел от ОС.

## Минимальный причинный diff

- Одна задача — одна ветка — один pull request.
- Меняйте только то, что нужно для критериев связанной issue; попутные
  рефакторинги, переименования и массовое форматирование (`ruff format`,
  `black`) не смешиваются с задачей.
- Новое публичное поведение — новый тест; изменение контракта явно
  указывается в описании PR и `CHANGELOG.md` со ссылкой на issue.
- Не хватает данных для классификации — возвращайте `unknown`, а не
  правдоподобный дефолт.

## Ветки и pull request

Полная модель — [docs/BRANCHING.md](docs/BRANCHING.md).

- `main` ← `epic/<slug>` или `roadmap/<номер>-<slug>` ← `task/<номер-issue>-<slug>`.
- Критическое исправление — `hotfix/<номер-issue>-<slug>` от `main`.
- Task-PR направляется только в свою epic/roadmap-ветку, а не в `main`.
- Прямой push в `main` запрещён и технически заблокирован защитой ветки.
- Состояния `pending`, `in_progress`, `skipped`, `cancelled` и отсутствующая
  проверка не считаются успехом CI.

## Что агент не делает автоматически

Без явного поручения владельца репозитория агент не выполняет:

- merge pull request;
- закрытие issue и отметку критериев;
- обновление epic/roadmap issue;
- удаление веток;
- повышение версии, release, создание тегов и публикацию пакета
  ([docs/RELEASING.md](docs/RELEASING.md)).

## Границы гарантий

Не усиливайте эти формулировки в коде, документации и ответах:

- покрытие метаданных, форм и BSL неполное; актуальные пробелы —
  [docs/bsl_coverage_matrix.md](docs/bsl_coverage_matrix.md),
  [docs/search_coverage.md](docs/search_coverage.md) и «Известные
  ограничения» [README.md](README.md);
- разрешённые `data_path` и связи могут быть недоказанными и помечаются как
  неполные или деградировавшие;
- динамические конструкции форм анализируются консервативно или пока не
  анализируются;
- метрики покрытия — индикатор, а не гарантия корректности;
- санитизация диагностики имеет документированные границы
  ([docs/diagnostic_sanitizer.md](docs/diagnostic_sanitizer.md)) и не
  обезличивает исходный код, метаданные и содержимое контекста; решение о
  передаче результата внешней LLM принимает потребитель.
