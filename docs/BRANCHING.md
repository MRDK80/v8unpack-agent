# Модель ветвления

Документ описывает, как организованы ветки и pull request в этом репозитории.
Правило-основа: **одна задача — одна ветка — один pull request**.

## Типы веток

| Ветка | База | Назначение | Как попадает дальше |
| --- | --- | --- | --- |
| `main` | — | Стабильное состояние продукта | только merge PR |
| `epic/<slug>` или `roadmap/<номер>-<slug>` | `main` | Интеграционная ветка планового релиза | PR в `main` |
| `task/<номер-issue>-<slug>` | соответствующая `epic/*` или `roadmap/*` | Одна задача из состава эпика | PR в свою epic-ветку |
| `hotfix/<номер-issue>-<slug>` | `main` | Критическое исправление вне плана | PR в `main` |

Ветка задачи всегда создаётся от подтверждённой базы, а не от произвольного
локального состояния. Если база выбрана неверно, ветка пересоздаётся.

## Поток изменений

1. Плановый релиз: `main` → `epic/*` → `task/*` → PR в `epic/*` → PR `epic/*` в `main`.
2. Критическое исправление: `main` → `hotfix/*` → PR в `main`.

Прямой push в `main` запрещён. Исключение возможно только по отдельному явному
решению владельца репозитория, а не как штатный режим работы, в том числе для
срочных исправлений.

## Требования к pull request

PR считается готовым к ревью, когда выполнено всё перечисленное:

- изменения соответствуют acceptance criteria связанной issue;
- в diff нет посторонних правок, не относящихся к задаче;
- `pytest` локально проходит без падений;
- CI успешен для текущего head SHA ветки, без pending и неизвестных проверок;
- в изменениях нет абсолютных путей, литеральных разделителей пути Windows,
  имён внутренних хостов, баз и строк подключения;
- пути строятся через `pathlib` или `os.path.join`, текст читается и пишется
  с явным UTF-8.

Состояния `queued`, `pending`, `in_progress`, `skipped`, `cancelled`,
`timed_out` и отсутствующая проверка не считаются успехом.

## Мерж и закрытие

Мерж task-PR в epic-ветку и мерж epic-ветки в `main` — два отдельных события,
каждое со своим прогоном проверок. Зелёный CI задачи до мержа не заменяет
проверку состояния целевой ветки после мержа.

Порядок завершения:

1. PR слит в подтверждённую целевую ветку;
2. зафиксирован новый SHA целевой ветки;
3. проверки нового SHA успешны;
4. issue синхронизирована с фактическими результатами и закрыта;
5. ветка задачи удалена либо указана причина её сохранения.

Дефект, найденный до мержа, исправляется в той же issue, ветке и PR. Отдельный
исправляющий PR по умолчанию не создаётся.

## Именование

- Слаг короткий, в нижнем регистре, слова через дефис.
- Номер issue в имени task- и hotfix-ветки обязателен.
- Пример: `task/214-cli-exit-codes`, `hotfix/221-unpack-crash`,
  `roadmap/158-cli-ux`.
