# Модель динамических операций формы

Opt-in library API `v8unpack_agent.dynamic_forms`, схема `dynamic_forms/1` (#213).
Основание — [исследование #212](research/dynamic_forms_issue212.md).
Модуль предоставляет неизменяемые записи и индекс. Он не ищет операции в BSL,
не изменяет декларативные элементы и не восстанавливает runtime-дерево формы.

## Закрытые типы

- `OperationKind`: `element_add`, `element_insert`, `element_delete`,
  `element_move`, `attributes_change`, `command_add`, `command_delete`, `property_set`.
- `TargetKind`: `form`, `element`, `command`, `attribute`, `unknown`.
- `ResolutionStatus`: `exact`, `partial`, `unresolved`.
- `ConditionKind`: `unconditional`, `if`, `loop`, `preprocessor`, `mixed`, `unknown`.
  Unconditional/mixed описывают сводную условность, не отдельное выражение guard.
- `BranchKind`: `then`, `else`, `elseif`, `body`.
- `TargetOrigin`: `declared`, `dynamic`, `form`, `unknown`.
- `PropertyKind`: закрытые 13 свойств из #212; значения нормализованы в нижний
  регистр. RU/EN распознавание относится к детектору, не конструктору модели.
- `DynamicReason`: закрытые технические причины, включая `unknown`,
  `receiver_unproven`, `computed_value`, `alias_invalidated`,
  `conflicting_bindings`, `branch_scope`, `unsupported_syntax`,
  `budget_exceeded`, `lexer_failure`.

Конструкторы требуют экземпляры enum, а не невалидированные строки.

## Источник и идентичность

`OperationSource` содержит относительный POSIX-путь модуля, SHA-256 снимка,
`start_line`, `end_line` и символьные `start_offset`, `end_offset`.
Строки начинаются с 1 и включительны; offsets начинаются с 0, интервал
полуоткрытый. Границы относятся к тому же текстовому снимку, хеш которого
выбран host. Проверка диапазона не доказывает, что источник существует или
что операция действительно содержится в нём: за это отвечает producer.

Пути проверяются одновременно по правилам POSIX/Windows через существующий
`validate_relative_module_path`: абсолютные, drive-relative, traversal,
неоднозначные разделители и зарезервированные имена отклоняются.
`operation_id(source, kind)` вычисляет стабильный ID из версии схемы,
снимка, пути, диапазона и вида. Порядок discovery в ID не входит. Изменение
снимка меняет ID; хеш не является подписью доверенного автора.

## Значения, цели и ссылки

`ResolvedValue` хранит собственный resolution, неизменяемый JSON scalar,
исходное выражение, техническую причину и признак `omitted`.
`None` при exact — литеральное null-подобное значение; отсутствие аргумента
задаётся явно `omitted=True`. Значения по умолчанию не угадываются.
Partial требует выражения, nonexact не может одновременно утверждать
вычисленное scalar-значение. Списки и словари как значения не принимаются:
batch-аргумент сохраняется выражением, не выдуманным списком runtime-объектов.

`EntityReference` задаёт вид, происхождение и resolution цели, необязательное
имя `ResolvedValue`, ID операции создания и `valid_in`.
**Ссылка на доказанно созданный элемент exact даже при partial-имени.**
Она обозначает символический результат места создания, не runtime-имя и
не единственный экземпляр в цикле. Для declared exact-цели требуется exact-имя;
объявленность и идентичность должен доказать producer.

У операции создания target описывает её создаваемую цель: dynamic exact-ссылка
указывает на собственный operation ID. Для setter target ссылается на ту же
операцию создания. Индекс проверяет существование ссылки, вид цели, снимок,
порядок определений и общий контекст процедуры; он не выполняет связывание
исходного BSL. Межпроцедурное доказательство в этот контракт не входит. Ссылка на реквизит
из batch изменения состава дополнительно требует точного имени реквизита:
одного ID batch-вызова недостаточно для различения нескольких реквизитов.

## Условия

`DynamicCondition` содержит ID, kind, источник, выражение,
`expression_resolution` и `runtime_truth`.
Полностью извлечённое выражение имеет `expression_resolution=exact`,
но истинность всегда `runtime_truth="unknown"`. Выражение не исполняется,
точность его извлечения не означает доказательство типов или значений операндов.

`ConditionReference` связывает operation с условием и ветвью.
`EntityReference.valid_in` задаёт контекст ветвей, в котором доказана привязка.
Условное создание и setter в той же then-ветви могут иметь exact-ссылку.
Она не обещает существование элемента при ложном условии. За пределы
доказанного контекста ссылка автоматически не переносится.
Индекс требует сохранить условия создающей операции в exact-ссылке.
Несовместимые или повторные ветви одного condition ID отклоняются.

`condition_context_complete=False` сохраняет неизвестную полноту контекста.
Пустой список условий при этом не означает unconditional. Вызов producer
должен явно установить полноту; модель её не выводит из пустого списка.
Список условий сохраняет порядок вложенности, выражения не объединяются
догадкой. Для loop допустима ветвь body, для if/preprocessor —
then/else/elseif. Конкретные грамматические ограничения задаёт producer.

## Операции и итоговый resolution

`DynamicFormOperation` хранит ID, kind, source, procedure, target,
`operation_resolution`, tuple аргументов `OperationArgument`,
property/value для setter, условия, полноту контекста и provenance.
Конструктор отклоняет неверные виды и несовместимые поля.

Имена аргументов фиксированы; отсутствующие значения передаются явно omitted:

| Вид | Аргументы |
|---|---|
| element_add | name, type, parent |
| element_insert | name, type, parent, before |
| element_move | parent, before; перемещаемая сущность в target |
| attributes_change | add_list, delete_list |
| command_add | name |
| element_delete / command_delete | удаляемая сущность в target |
| property_set | property_kind и value, отдельных arguments нет |

Exact требует доказанной цели и exact-значений обязательных аргументов.
Partial сохраняет доказанную операцию с nonexact-аргументами.
При недоказанном получателе разрешён только unresolved итог операции.
Условность не понижает статическую разрешимость автоматически.

Setter литеральной ширины с exact-ссылкой на созданную цель имеет exact итог,
хотя имя и итог создающей операции partial. Вычисляемое значение пути данных
делает setter partial. Неоднозначное происхождение получателя делает его
unresolved. Итог цепочки связанных кандидатов — отдельный контракт #215;
он не меняет статусы исходных операций задним числом.

## Индекс и сериализация

`DynamicOperationIndex(operations=(), conditions=())` принимает tuple frozen
записей. Дубликаты ID и висячие/несовместимые ссылки отклоняются.
Операции сортируются по пути, снимку, offsets, виду и ID; условия — по пути,
снимку, позиции и ID. Индекс создаётся host для выбранной формы; он не
объединяет разные конфигурации по похожим именам.
`select(kind=..., procedure=...)` возвращает tuple; имя процедуры сравнивается
через casefold. Сортировка не зависит от ОС и discovery.

`to_dict()` и `to_json()` возвращают отдельное представление dynamic operations
с `declared_elements_included=False`. Полный текст BSL не хранится в модели.
По умолчанию выражения скрыты, сохраняются наличие и хеш; для локального
анализа доступно `include_expressions=True`. Имена и литералы остаются
исходными данными и могут содержать чувствительную информацию: этот метод
не является обезличивателем и не предназначен для публикации реальных данных.
JSON каноничен по ключам, не допускает NaN/Infinity.

Пример с вычисляемым именем, условием и exact-ссылкой покрыт синтетическими
тестами `test_dynamic_forms_issue213.py`. Сборка записей не доказывает
корректность фактов в BSL: модель проверяет структуру, детектор и linker
должны предоставить доказательства происхождения.

## Границы этапа

Модуль не интегрирован с FormContext/runner/CLI и не запускает модели.
Детектор — #214, связывание — #215, измеримый data flow — решение #216,
framed-проекция — #217. Передача исходных значений в модель требует
[framed-контракта](untrusted_content_contract.md) и решения host.
