# Production runner

Модули `v8unpack_agent.runner` и `v8unpack_agent.cli` дают единую точку входа
для обработки уже распакованной выгрузки: один прогон — один post-run
report и один exit code.

Сама распаковка в задачу runner не входит: на вход подаётся каталог
текстового слоя, полученный ранее. Модель и writer отчёта описаны в
[docs/run_report.md](run_report.md).

## Разделение ответственности

| Модуль | Роль |
| --- | --- |
| `runner` | чистая библиотека: собирает `PostRunReport`, не пишет файлы и не завершает процесс |
| `cli` | разбор аргументов, запись отчёта, владение exit code |

Такое деление позволяет вызывать пайплайн из другого кода и из тестов без
побочных эффектов, а также проверять политику кодов возврата отдельно.

## Запуск

После установки пакета доступен console script:

```bash
v8unpack-agent-run <корень_выгрузки> --report-path <путь_к_отчёту>
```

Равнозначный вызов без установки:

```bash
python -m v8unpack_agent.cli <корень_выгрузки> --report-path <путь_к_отчёту>
```

### Аргументы

| Аргумент | Назначение |
| --- | --- |
| `export_root` | позиционный; корень уже распакованной выгрузки |
| `--report-path` | обязательный; путь к JSON-файлу отчёта, значения по умолчанию нет |
| `--mode` | `config` или `external`; режим сканирования форм |
| `--skip-common-modules` | не обнаруживать общие модули |
| `--skip-skd` | не извлекать артефакты СКД |
| `--max-prompt-chars` | лимит длины промпт-фрагмента; `-1` без ограничения |

Каталог-родитель для `--report-path` должен существовать заранее: writer
не создаёт каталоги и при его отсутствии возвращает код 5.

## Политика exit code

| Код | Условие | Отчёт |
| --- | --- | --- |
| 0 | все объекты `complete` | записан, `completed=true` |
| 2 | ошибка аргументов или `export_root` не каталог | не создаётся |
| 3 | degraded: есть `partial` или `failed` | записан, `completed=true` |
| 4 | управляемая фатальная ошибка пайплайна | записан, `completed=false` и `fatal_error` |
| 5 | ошибка записи отчёта | запись не гарантируется |
| 6 | фатальная ошибка и ошибка записи одновременно | не записан |

Degraded считается неуспешным завершением процесса: неполный LLM-контекст
не должен выглядеть как успех для вызывающей автоматизации. Код 6 выделен
отдельно, чтобы отличать единичный отказ от полной потери
наблюдаемости: при нём ни код возврата, ни отчёт не дают деталей об
объектах.

## Стадии обработки формы

`build_form_context` — единственная композитная обработка: внутри неё уже
выполняются разбор `.elem.json` и декодирование атрибутов объекта,
поэтому runner не вызывает их повторно. Классификация результата
детерминирована и идёт строго в этом порядке:

| Приоритет | Условие | Статус | `stage` | `reason_code` |
| --- | --- | --- | --- | --- |
| 1 | `build_form_context` бросил исключение | `failed` | `build_context` | `context_build_error` |
| 2 | сборка промпт-фрагмента бросила исключение | `failed` | `build_context` | `prompt_build_error` |
| 3 | elem-индекс не построен | `partial` | `parse_elem` | из `unindexed_reason_code` либо `elem_index_unavailable` |
| 4 | непустой `FormEntry.warnings` | `partial` | `scan` | нормализованный код первого предупреждения |
| 5 | иначе | `complete` | — | — |

Фиксированный порядок нужен, чтобы при одновременном наличии нескольких
причин в отчёт попадала одна предсказуемая пара `stage`/`reason_code`.

### Что не считается деградацией

- `object_attributes is None` — отсутствие контекста владельца;
- отсутствие owner-уровня в layout выгрузки;
- отсутствие BSL у elem-only формы.

Это ожидаемые состояния пакета, а не неполнота прогона.

## Общие модули и СКД

Статус общего модуля определяется только функцией `common_module_status`,
а статус артефакта СКД — `skd_status`. Своего mapping runner не заводит.

`SkdResult` не несёт ни имени, ни пути, поэтому идентификатор артефакта
строится как порядковый номер позиции в `SkdBatchResult.results`, например
`skd_artifact_001`. Значение детерминировано в рамках одного входного
дерева, но не является устойчивым идентификатором отчёта между разными
выгрузками.

Пропуск группы через `--skip-common-modules` или `--skip-skd` не создаёт
результатов со статусом `excluded`: обнаружение не выполняется, поэтому
таких объектов в отчёте просто нет.

## Фатальные ошибки

| `reason_code` | Когда возникает |
| --- | --- |
| `scan_failed` | отказ стадии обнаружения форм |
| `common_modules_failed` | отказ обнаружения общих модулей |
| `skd_failed` | отказ пакетного извлечения СКД |

Поле `error_type` получается из имени класса исключения и приводится к
машинному коду. Граница слов вставляется после строчной буквы или цифры,
поэтому акроним в начале имени остаётся слитным: `ValueError` даёт
`value_error`, а `OSError` — `oserror`.

Нераспознанное имя заменяется на `runtime_error`.

## Нормализация кодов сканера

Сканер публикует коды предупреждений в верхнем регистре — это часть
отображаемого формата сообщения. Модель отчёта требует нижний регистр,
поэтому регистр приводится на стороне runner. Правила:

- код сначала распознаётся по whitelist сканера;
- текст предупреждения к нижнему регистру не приводится;
- после нормализации значение проверяется регулярным выражением;
- legacy-предупреждение без маркера и повреждённый маркер дают
  `scan_warning_unclassified`.

Последнее важно потому, что `partial` и `failed` требуют непустого
`reason_code`: без fallback-кода легитимное предупреждение старого формата
сорвало бы валидацию отчёта.

## Идентификаторы и обезличивание

Идентификатор формы берётся из `FormContext.metadata['form_path']` — уже
относительного posix-пути, а не из `FormEntry.form_path`, который всегда
абсолютен. Корневой префикс и разделители конкретной ОС снимаются, так что
в отчёт попадают только относительные значения.

Сообщения об ошибках сводятся к одной строке и ограничиваются по длине.
Если сообщение не прошло проверку безопасности модели — например,
содержит traceback-маркер или абсолютный путь, — результат записывается
без сообщения. Целостность отчёта важнее диагностической подробности.

Предупреждения уровня прогона не привязаны к объекту и в JSON не попадают.
Вызывающий код может взять их из `RunOutcome.scan_warnings`; CLI печатает
только их количество.

## Библиотечный вызов

```python
from pathlib import Path

from v8unpack_agent.run_report import write_post_run_report
from v8unpack_agent.runner import RunOptions, run_pipeline

options = RunOptions(
    export_root=Path("unpacked"),
    include_skd=False,
    max_prompt_chars=20000,
)
outcome = run_pipeline(options)

if outcome.degraded:
    pass  # решение принимает вызывающий код

write_post_run_report(outcome.report, Path("post-run.json"))
```

`run_pipeline` не бросает исключений пайплайна: управляемая фатальная
ошибка попадает в `fatal_error`, а ошибка отдельного объекта — в его
результат. Исключение может бросить только writer.

## Переносимость

Пути строятся через `pathlib`, текст читается и записывается как UTF-8,
стандартные потоки CLI переводятся в UTF-8. Сценарий пригоден для POSIX-
и NT-сред, включая конфигурации без GPU.
