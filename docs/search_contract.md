# Контракт общего поиска (#322)

Модуль `v8unpack_agent.search_contract` задаёт неизменяемые типизированные
модели общего поиска эпика #320: документ, запрос, результат и связь
владельца с артефактом. Контракт не зависит от сканера, эмбеддера и формата
хранения: модуль не читает файлы, не вызывает провайдера, не строит индекс и
не исполняет найденный код.

Основания: стабильный контракт модулей #203 ([`modules.md`](modules.md)),
ключ формы `FormRagIndex` ([`form_rag.md`](form_rag.md)), инвентаризация #202
и исследование поискового представления #321
([`research/search_representation_issue321.md`](research/search_representation_issue321.md)).

## Импорт

```python
from v8unpack_agent.search_contract import (
    ArtifactRef,
    OwnerLink,
    OwnerRef,
    SearchDocument,
    SearchDocumentSet,
    SearchFilters,
    SearchHit,
    SearchQuery,
    SearchResult,
    TextSpan,
)
```

Корневой `v8unpack_agent.__init__` не расширяется; API форм и модулей не
меняется.

## Идентичность

| Вид | `artifact_id` | Источник полей |
|---|---|---|
| `module` | `<owner_kind>:<metadata_type>:<owner_name>:<module_kind>` | `ModuleEntry`; строка равна `ModuleEntry.module_id` |
| `form` | `form:<object_type>/<object_name>/<container_name>/<form_name>` | четвёрка `FormRagIndex` / `drift_checker.form_key` |
| `owner` | `owner:<owner_kind>:<metadata_type>:<owner_name>` | поля владельца `ModuleEntry` |

Фрагмент (`document_id`): `<artifact_id>#<процедура>`; окно строк без
процедуры — `<artifact_id>#L<начало>-<конец>`; артефакт целиком —
`<artifact_id>`.

Принятые решения по формату #321:

- **Модуль конфигурации.** У `configuration` поля `metadata_type` и
  `owner_name` равны `None`, поэтому id содержит пустые сегменты:
  `configuration:::session`. В eval-наборах #321 использована запись
  `configuration:-:Configuration:session`; она не каноническая. Наборы #321
  не менялись, расхождение закреплено тестом и должно учитываться в #329.
- **Экранирование.** Сегменты id модуля не экранируются: `owner_kind` и
  `module_kind` — закрытые наборы, `metadata_type` — ASCII-идентификатор,
  `owner_name` — идентификаторы 1С через точку; `:`, `#` и `/` в них
  невозможны и отклоняются. Сегменты ключа формы приходят из имён каталогов
  (у внешних обработок — имя каталога распаковки) и экранируются функцией
  `encode_id_segment`: `%`→`%25`, `/`→`%2F`, `:`→`%3A`, `#`→`%23`.
  Без этих символов id формы равен `"form:" + form_key(...)`. Управляющие
  символы отклоняются.
- **Общие формы.** Ключ `scan_forms` для `CommonForm` содержит пустое
  `object_name`: `form:CommonForm//CommonForm/<Форма>`.
- **Кириллица и регистр.** Id хранится как есть. Сравнение и поиск дубликатов
  выполняются по `identity_key()`: NFC-нормализация и `casefold`, как
  проверка дубликатов `module_id` в `ModuleIndex`. Id, различающиеся только
  регистром, считаются одним артефактом.
- **Одинаковые короткие имена.** Разные владельцы различаются `metadata_type`,
  `owner_name` (у команд — `<Объект>.<Команда>`) или `object_name` формы.

## Модели

- `OwnerRef(owner_kind, metadata_type, owner_name)` — правила как у
  `ModuleEntry`.
- `ArtifactRef(artifact_kind, owner, module_kind, form_key, source_path)` —
  конструкторы `from_module_entry()`, `form()`, `owner_card()`. У формы
  `owner` может быть `None`, если адаптер не установил владельца.
- `TextSpan(start_line, end_line)` — строки с 1, обе границы включительно,
  после удаления ведущего BOM и нормализации CRLF/CR в LF (как в
  `to_llm_module_fragment`, #345). `0`, отрицательные значения, `bool`,
  нецелые числа и `end_line < start_line` отклоняются.
- `SearchDocument(artifact, text, procedure, span)` — непустой текст
  артефакта или фрагмента; `procedure` — идентификатор 1С.
- `SearchDocumentSet` — отсортированный набор документов.
- `SearchFilters`, `SearchQuery`, `SearchHit`, `SearchError`, `SearchResult`.
- `OwnerLink(owner, artifact, basis)` — связь владельца с модулем или формой.

`source_path` — относительный POSIX-путь от корня выгрузки. Абсолютные пути,
диск, UNC, обратная косая черта, `..`, `.`, пустые сегменты, `:` и имена
устройств отклоняются (`validate_relative_source_path`).

## Фильтры

`SearchFilters(artifact_kinds, module_kinds, owner_kinds, metadata_types,
owner_names)`; `None` — измерение не ограничено, пустой набор — ошибка.
Внутри измерения — ИЛИ, между измерениями — И. `module_kinds` пропускает
только модули. Фильтры владельца не пропускают артефакты без владельца.
`owner_names` сравниваются по `identity_key`, `metadata_types` — точно.
Значения нормализуются в отсортированные кортежи без повторов.

## Состояния результата

| `status` | Попадания | Смысл |
|---|---|---|
| `exact` | ровно одно, `exact_id` или `exact_name` | однозначное точное разрешение |
| `ambiguous` | два и более точных | полный список кандидатов, `top_k` не применяется |
| `semantic` | от 1 до `top_k`, только `semantic` | смысловые кандидаты |
| `empty` | нет | кандидатов нет, ошибки нет |
| `error` | нет | поиск не выполнен; задан `SearchError` |

Режим запроса: `auto`, `exact` (смысловая выдача запрещена), `semantic`
(точные состояния запрещены). Каждый артефакт встречается в выдаче не больше
одного раза, все попадания обязаны проходить фильтры запроса.

Коды ошибок: `embedder_failed`, `incompatible_index`, `index_not_ready`,
`internal`, `invalid_vector`. Сообщение фиксировано по коду; исходные
исключения, пути и ответы провайдера в результат не попадают. Некорректный
запрос (пустой текст, управляющие символы, `top_k < 1`) отклоняется при
создании `SearchQuery` (`ValueError`).

## Происхождение и оценка сходства

`SearchHit` хранит раздельно:

- происхождение: `method` (`exact_id`, `exact_name`, `semantic`),
  `matched_field` (`artifact_id`, `owner_name`, `form_name` — только для
  точных) и `document_id` найденного фрагмента (только для смысловых);
- оценку: `similarity` — только у смысловых попаданий, конечное число.

`similarity` — оценка конкретного поисковика (косинус, BM25 и т. п.), а не
вероятность правильного ответа. Она не калибрована (#321) и между разными
поисковиками не сравнима; диапазон не ограничивается.

## Порядок и дубликаты

- `exact` и `ambiguous` — по `identity_key(artifact_id)`, затем по id.
- `semantic` — по убыванию `similarity`, при равенстве по артефакту.
- `SearchDocumentSet` — по артефакту, затем целый документ, процедуры,
  окна строк по номерам.

Допустимы: несколько документов одного артефакта (фрагменты, в том числе с
перекрывающимися окнами), одинаковый текст у разных документов, одинаковые
короткие имена у разных владельцев. Отклоняются: повтор `document_id` без
учёта регистра, разные описания одного `artifact_id` в наборе, повтор
артефакта в выдаче.

## Сериализация

`to_dict()` / `from_dict()` у всех моделей; `from_dict()` проверяет точный
набор ключей и пересчитанные id. `to_json()` у `SearchResult` и
`SearchDocumentSet`: сортированные ключи, UTF-8 без экранирования,
`allow_nan=False`, LF в конце. Схема — `search_contract/1`.

Текст документа не сериализуется по умолчанию: в `to_dict()` попадают
`text_chars` и `text_sha256`. Исходный код не считается обезличенным
автоматически, поэтому текст включается только явным `include_text=True`;
`from_dict()` документа требует текст и сверяет его с `text_sha256`.

## Связи владельца

`OwnerLink.basis`:

- `module_entry` — владелец совпадает с владельцем модуля из `ModuleEntry`;
- `form_key` — `metadata_type` и `owner_name` владельца совпадают с
  `object_type` и `object_name` ключа формы;
- `unconfirmed` — связь не доказана; `confirmed` равно `False`.

## Ограничения для следующих задач

Адаптеры форм, модулей и карточек владельцев (#323) описаны в
[`search_corpus.md`](search_corpus.md).

- #323: владелец формы из ключа `scan_forms` устанавливается только для
  4-уровневого layout. У общих форм `object_name` пуст, у внешних форм
  `object_name` — имя каталога распаковки, а владелец модуля объекта
  (#351) берёт имя из `ExternalDataProcessor.json`; такие связи остаются
  `unconfirmed`, пока адаптер не докажет соответствие. Синонима владельца в
  `ModuleEntry` нет.
- #324: имя процедуры должно быть идентификатором 1С; для тел без процедур —
  окна `#L<a>-<b>` в координатах `TextSpan`. Повтор процедуры без учёта
  регистра в одном артефакте отклоняется набором документов.
- #326: точное разрешение возвращает `exact` или `ambiguous` по
  `identity_key`; смысловой fallback — `semantic` с агрегацией до одного
  попадания на артефакт.
- #329: каноническая форма id модуля конфигурации отличается от eval-наборов
  #321.
- Выбор модели эмбеддингов и повторный замер в #322 не выполнялись.

Правила фрагментации #324, исходные срезы и отдельный `search_text`,
окна больших процедур и диагностика описаны в
[`search_fragments.md`](search_fragments.md). Контракт `search_contract/1`
и исходный корпус не изменяются.
