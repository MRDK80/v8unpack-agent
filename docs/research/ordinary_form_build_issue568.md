# Сборка обычных форм через v8unpack (#568)

Проверка выполнена на двух локальных синтетических артефактах: CF с пятью
обычными формами элементов справочников и EPF с одной обычной формой
обработки с командными панелями. Обе выбранные формы имеют
`Тип формы = "0"` и `Версия элементов формы = "0-27"`. Среда: Linux x86-64,
Python 3.12, saby v8unpack 1.2.13, учебная 1С:Предприятие 8.5.4.1291.
Идентификаторы, модули и бинарники образцов в репозиторий не включены.

## Воспроизведение

1. В Конфигураторе выгрузить исходные синтетические CF и EPF в XML с
   `Form.bin`. Для CF использовать отдельную пустую файловую базу.
2. Для каждого образца запустить пробу. `FORM_DIR` — относительный каталог
   формы в дереве `v8unpack.extract`, например
   `Catalog/Probe/CatalogForm/Item` или `Form/Main`. `FORM_BIN` — бинарник
   именно этой формы из шага 1. `WORK` должен ещё отсутствовать.

   ```bash
   python -m scripts.probe_ordinary_form_build_issue568 "$OWNER" "$FORM_DIR" "$FORM_BIN" "$WORK"
   ```

3. Проба выполняет `v8unpack.extract(..., processes=1, options={"auto_include": False})`,
   сверяется с `parse_elem_json(write_index=False)`, отдельно вызывает
   `OrganizerFormElem.pack` и дважды вызывает `v8unpack.build` с теми же
   настройками. `rebuilt.cf` / `rebuilt.epf` собираются из нормализованного
   дерева с заново записанными файлами формы. `control.cf` / `control.epf`
   отличаются подстановкой оригинальных потоков `form` и `module` для
   выбранной формы непосредственно перед сжатием стадии `encode_stage_1`.
   Обёртка в пробе использует внутреннюю стадию именно версии 1.2.13.
4. Загрузить каждый CF через `DESIGNER /F "$TEST_BASE" /LoadCfg "$BUILT_CF"`,
   применить через `/UpdateDBCfg` и выгрузить через `/DumpConfigToFiles "$XML_DIR"`.
   В режиме обычного приложения открыть список выбранного справочника
   и форму создания элемента, затем закрыть её без записи. EPF выгрузить
   командой `DESIGNER /F "$TEST_BASE" /DumpExternalDataProcessorOrReportToFiles
   "$OUTPUT_XML" "$BUILT_EPF"`. Собранный EPF открыть в той же тестовой базе
   в режиме обычного приложения, в том числе через `/Execute "$BUILT_EPF"`.
5. Для EPF повторить `v8unpack.extract` и сравнить `*.elem.json` и `*.obj.bsl`.
   Для обеих XML-выгрузок извлечь два потока каждого сопоставленного
   `Form.bin` через `v8unpack.container.Container`. Сравнить `module`
   побайтно, `form` как списки из `v8unpack.helper.brace_file_read`, с
   сохранением порядка и точных значений. Такой разбор исключает отличия
   отступов и переносов между узлами сериализации.

## Результаты

| Проверка | Синтетический CF | Синтетический EPF |
| --- | --- | --- |
| Индекс агента выбранной формы | Успех, 6 записей | Успех, 4 записи |
| Отдельный `OrganizerFormElem.pack` | Успех | Успех |
| `v8unpack.build`, контроль и вариант без `Form.bin` | Два CF записаны | Два EPF записаны |
| Конфигуратор | Оба CF загружены и выгружены в XML | Оба EPF выгружены в XML |
| Открытие выбранной формы из варианта без `Form.bin` | Форма нового элемента открылась | Окно обработки с командными панелями открылось |
| Повторный `v8unpack.extract` на варианте без `Form.bin` | Ошибка чтения контейнера | Нормализованные `elem.json` и BSL побайтно совпали с исходным извлечением |
| Сравнение потоков XML-выгрузок 1С | Для обоих CF у всех пяти форм совпали модуль и разобранный макет | В обоих EPF модуль совпал. Разобранные макеты различаются между исходным, контрольным и собранным EPF |

В CF первый сбой повторного извлечения возникает ещё до декодирования
метаданных: `ValueError: invalid literal for int() with base 16: b'00\r\n0000'`.
CF содержит два контейнера. В 1.2.13 `Container64.build` получает ненулевое
начальное смещение, но `write_table_off_content` передаёт смещение заголовка
как абсолютный адрес в `Document.write_block`. Оглавление второго
контейнера пишет поверх данных первого. 1С загрузила CF, и сравнение форм
через её XML-выгрузку прошло. Приёмка через непосредственное повторное
извлечение этим выпуском upstream остаётся открытой.

У EPF повторное извлечение подтверждает сохранность нормализованных
данных, но в разобранном макете XML-выгрузки 1С собранного EPF отличаются
30 строковых значений. Контрольный EPF с подставленными оригинальными
потоками также отличается от исходного после выгрузки в 1С. Правило
эквивалентности для этих значений пока не установлено.

На дополнительном upstream-образце с вложенной включаемой панелью проба
`OrganizerFormElem.pack` для выбранной формы успешна, а сборка всего EPF
без `auto_include` останавливается на `KeyError` для записи `-pages-` внутри
включаемой панели, в `FormElements27/Panel.py::encode_pages`. При
`auto_include=True` EPF собрался, но повторное извлечение дало полное
совпадение `elem.json` только у одной из пяти обычных форм. Сборка областей
с таким разбиением требует отдельной проверки.

## Входы для #572 и #571

| Источник | Что требуется сохранить |
| --- | --- |
| `<stem>.json` | Заголовок формы, тип и версия, параметры модуля, упорядоченный `form` со структурой, ссылками и ещё не интерпретированными позициями. Upstream использует этот каркас в `FormCore.encode_nested_includes` и `write_old_encode_object`. |
| `<stem>.id.json` | UUID формы, связанный с метаданными объекта-владельца. |
| `<stem>.elem.json` | Полный `tree`, `data`, `props`, `params`, `commands` с исходным порядком и типами. Здесь, в частности, находятся данные страниц, позиции элементов, ссылки и необработанные значения `raw`. |
| `<stem>.obj.bsl` | Извлечённый модуль. При отсутствии файла upstream может записать пустой модуль, поэтому потерю исходного модуля нужно диагностировать до сборки. |
| Дерево владельца | Тип владельца, относительное место формы, UUID и окружение для отдельной сборки всего контейнера. Для включаемых областей требуется сохранять и проверять их зависимости. |

В проверенном EPF удаление файла элементов, заголовка, идентификатора или
ключа `form` приводило к ошибке сборки либо повторного извлечения.
Удаление модуля позволяло получить повторно извлекаемый EPF с деревом,
но терялось содержимое модуля. Эти проверки проводились на копиях.

`FormArtifact` даёт пути к модулю и метаданным и признаки извлечения.
`form_elements_index.json` содержит проекцию полей для анализа.
Для восстановления нужны сырые файлы upstream и сведения об их
происхождении. Выгрузку, в которой осталась только проекция, предстоит
извлечь повторно. В #572 требуется описать и проверять набор пригодных
входов. В #571 требуется проверить восстановление, редактирование одного
свойства и сохранность остальных блоков. Наблюдения о двух контейнерах и
вложенных панелях относятся к upstream 1.2.13.
