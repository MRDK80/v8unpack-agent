## 2. Метод отделения ссылок от определений

### 2.1 Правила доказательства

Текстовое присутствие UUID в выгрузке доказательством не является: UUID уже
присутствует минимум в самом ссылочном дескрипторе. Для каждого вхождения
фиксируется структурная роль:

- нормализованный JSON-pointer (числовые индексы массивов → `*`, если конкретный
  индекс не является частью доказанного контракта);
- тип контейнера (объект/массив, арность, набор ключей-соседей);
- позиция относительно известных тегов заголовка;
- признак «ссылочный дескриптор» либо «кандидат определения».

Кандидатом определения позиция считается только при одновременной доказуемости
трёх компонентов в одном структурном контексте: UUID, имя объекта и тип
метаданных.

### 2.2 Четыре класса preflight

| Класс | Доказательство |
|---|---|
| `definition_known` | UUID найден в позиции определения, которую текущий `scan_forms` уже считает распознанной |
| `definition_unknown_layout` | UUID найден в иной потенциальной позиции определения, где одновременно доказуемы UUID, тип метаданных и имя |
| `reference_only` | Все найденные позиции — ссылочные дескрипторы, кандидата определения нет |
| `ambiguous` | Структурные позиции есть, но доказательств для отделения определения от ссылки недостаточно |

Preflight проходит всю распакованную конфигурацию, а не только файлы форм.

### 2.3 Обезличивание

Допустимая форма пути:

```text
<MetadataType>/<Object>/header/*/...
header/*/identity/*
```

Недопустимо: абсолютные пути, локальные имена объектов, сами UUID, полные
фрагменты production JSON, таблица соответствия `Uxx → UUID`, короткие
SHA-маркеры в публичном отчёте. В отчёте используются только ранги `U01`–`U48`,
отсортированные по убыванию числа вхождений; соответствие существует лишь в
памяти процесса.

### 2.4 Запреты вывода типа

Тип UUID не выводится по соседнему имени, по типу формы, по доминирующей
категории и по частоте. Частота сама по себе общий контракт не доказывает.
Ранее полученные количества `ChartOfCharacteristicTypeRef` (80) и
`ExchangePlanRef` (18) относятся к уже разрешённым типам и как признак природы
остатка не используются: у неразрешённого значения известен только `Ref#uuid`,
его будущий префикс неизвестен.

## 4. RCA распознанной позиции

Текущий агрегат «UUID есть в `reference_types`, но не разрешён» равен 0,
поэтому явного RCA несогласованности индекса на этом baseline нет.

Если расширенный preflight обнаружит хотя бы один `definition_known`, это
противоречит baseline и требует отдельного разбора до любых правок:

1. Почему распознанная позиция не попала в `reference_types`.
2. Не пропускает ли `scan_forms` конкретный тип метаданных.
3. Нет ли конфликта UUID или недетерминированной перезаписи записи индекса.
4. Совпадает ли имя типа с контрактом `_infer_object_type`
   (`v8unpack_agent/catalog_resolver.py`).
5. Воспроизводится ли результат на втором проходе.

До завершения RCA такой UUID в индекс автоматически не добавляется.

## 6. Решение по каждому структурному классу

Заполняется после разделов 3–5. Правила принятия решения фиксированы заранее:

- `definition_unknown_layout` → `implement` только если одна структурная схема
  повторяется у нескольких UUID, обязательные поля (UUID + имя + тип
  метаданных) присутствуют всегда, схема не встречается в ссылочной роли,
  добавление позиции не меняет ни одну из 14 422 успешных резолюций и не
  затрагивает нессылочные типы и `data_path`. Иначе — `need more evidence`.
- `reference_only` → `keep unresolved`. Фиксируется только отсутствие
  доказанного определения. Формулировки «удалённый объект», «объект расширения»,
  «остаток обновления» без отдельного доказательства не используются.
  Implementation issue на расширение resolver не создаётся.
- `ambiguous` → `need more evidence`, fallback `Ref#uuid` сохраняется.
- Расширение resolver только ради роста coverage запрещено.

## 8. Риски ложноположительной резолюции

- Присвоение типа по соседнему имени или по доминирующей категории формы.
- Совпадение layout ссылочного дескриптора и кандидата определения: одна и та
  же схема в обеих ролях делает признак неразделяющим.
- Конфликт UUID: две записи претендуют на один UUID, порядок обхода определяет
  победителя — недетерминированная перезапись индекса.
- Смешение измерений #143 и #163: отсутствие `object_attributes` — не тот же
  дефект, что неизвестный UUID внутри них.
- Ослабление fallback: любая неопределённость должна оставлять `Ref#uuid`.
