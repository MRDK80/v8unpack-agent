## 2. Метод отделения ссылок от определений

### 2.1 Позитивный контроль обязателен

Первые версии инструмента давали ноль кандидатов определения и «чистый»
`reference_only` по всем 48 UUID. Контрольная группа это опровергла: 120 UUID,
которые resolver разрешает и у которых определение существует по построению,
тоже дали ноль кандидатов. Детектор был слеп.

Правило метода: **отсутствие срабатывания детектора не является доказательством
отсутствия определения**. Любой отрицательный результат проверяется группой, для
которой ответ известен заранее.

### 2.2 Роль файла определяется структурно

Тип объекта проект выводит из пути (`_infer_object_type`), поэтому позиция
определения — это пара «роль файла × указатель». Файлом объекта считается путь
вида `<Вид>/<Имя>/<Вид>.json` для **любого** вида, без белого списка: жёсткий
список видов ранее прятал `ChartOfCharacteristicType`, `DefinedType`,
`CommonModule` и другие.

Роли: `object_other` 13 572, `object_metadata` 3920, `config_other` 3.
Виды файлов объекта (top): CommonPicture 712, CommonModule 651, Enum 395,
XDTOPackage 266, InformationRegister 216, CommonTemplate 195, Document 185,
Constant 183, CommonForm 162, DataProcessor 158, Catalog 142, Report 139.

### 2.3 Слот идентичности выведен из контроля

| Слот | Покрытие контроля | Попаданий на UUID | Файлов на UUID | UUID остатка |
|---|---:|---:|---:|---:|
| `object_metadata / bare / header/*/*/*` | 100.0% (120 из 120) | 1.00 | 1 | 28 |

Критерий: роль `object_metadata`, покрытие не ниже 50%, не более 1.5 попадания
на UUID, один файл на UUID. Плотные слоты (более 5 попаданий на UUID) исключены.
Слотов иного layout с поддержкой контроля не найдено ни одного.

### 2.4 Обезличивание

Публикуются: ранги `U01`–`U48`, нормализованные указатели, числовые слоты, виды
метаданных, платформенно-стандартные имена. Не публикуются: UUID, имена объектов,
форм и реквизитов, пути, соответствие `Uxx → UUID`. Конкретика доступна локально
через `--local-names` и `--annex`; вывод этих режимов не коммитится (CSV покрыт
маской `*.csv` в `.gitignore`).

## 4. RCA класса `definition_known`

28 UUID найдены в позиции идентичности, но отсутствуют в `reference_types`.
Аномалий индекса — **ноль**: случай «вид входит в `REFERENCE_TYPE_PREFIXES` и ни
один слот файла не проиндексирован» не встретился.

проиндексированных слотов ноль. Это граница контракта #88, а не дефект.

### 5.3 Гипотеза платформенных типов

Локальный разбор (`--local-names`, не публикуется) показал устойчивые профили:
у ранга с 575 вхождениями это реквизиты-хранилища, у другого — таблицы значений,
далее списки значений, деревья значений, построители отчёта, уникальные
идентификаторы. Это указывает, что остаток адресует **типы, объявляемые
платформой, а не конфигурацией**, — тогда отсутствие позиции определения в
выгрузке закономерно, а `Ref#uuid` является корректным результатом.

Гипотеза не считается доказанной: выводить тип по имени соседнего реквизита
запрещено условиями #143. Требуется независимая проверка — прогон инструмента на
второй выгрузке другой конфигурации. Если те же UUID присутствуют и там, они
платформенные константы; сопоставление по именам для этого вывода не нужно.

## 8. Риски ложноположительной резолюции

- Расширение `REFERENCE_TYPE_PREFIXES` видами DocumentJournal, InformationRegister,
  Report, DataProcessor: 18 UUID и 103 вхождения получили бы имя `<Kind>Ref.<Имя>`
  для типов, у которых ссылочной формы нет.
- Резолюция по позиции идентичности без проверки слота: 10 UUID и 55 вхождений —
  объектные, списочные и менеджерские грани — получили бы ложное ссылочное имя.
- Вывод типа по имени соседнего реквизита: профили 5.3 убедительны, но
  доказательством не являются и в решения не заложены.
- Позиционные счётчики как веса: 4377 позиций против 1301 вхождения; у U03
  1463 позиции при 83 вхождениях, у U01 221 позиция при 575.
- Слепота детектора: продемонстрирована позитивным контролем, поэтому любой
  нулевой результат без контрольной группы недействителен.
- Смешение с #163: отсутствие `object_attributes` — другой дефект.

## 9. Follow-up issues

1. **Кросс-конфигурационная проверка гипотезы платформенных типов.** Прогон
   `examples/unresolved_refs_report.py` на второй выгрузке; критерий — совпадение
   UUID остатка между конфигурациями.
2. **Статическая таблица платформенных типов** `UUID → имя`. Только после пункта 1.
   Критерий строже роста coverage: фиксированная таблица, синтетические fixtures,
   неизменность 14 422 существующих резолюций, неизменность нессылочных типов и
   `data_path`, сохранение fallback при любой неопределённости.
3. **Нессылочные виды метаданных и типовые грани** (объект отчёта, объект
   обработки, менеджер записи регистра, список журнала документов) — отдельный
   контракт имён, не через `REFERENCE_TYPE_PREFIXES`.
4. **Машинные коды `scan_warnings`**: все 49 предупреждений без кодов, агрегация
   и мониторинг невозможны.
5. **Документирование границы контракта** в `docs/scan_forms.md`: перечислить виды,
   для которых имя ссылочного типа не строится, и указать, что `Ref#uuid` в этом
   случае корректный результат.

Для `reference_only` implementation issue не создаётся.
