# ADR: контракт представления недоверенного содержимого в LLM-выводе (#457)

Статус: предложен (T2 эпика #455). Основа: инвентаризация и эталоны T1 (#456,
`tests/golden_issue456/`) на `roadmap/455-untrusted-content-contract` @ `b9aed2ab`.

## Граница документа

ADR задаёт только форму представления текста, полученного из выгрузки, в
выводах, предназначенных для LLM. Он не утверждает и не обещает устойчивость
какой-либо модели к prompt injection, защиту от поведения модели или клиента и
корректность ответа модели. Контракт даёт потребителю детерминированный способ
отделить данные выгрузки от служебной структуры вывода; как потребитель
использует это разделение, вне контракта.

## Исходное состояние (по эталонам T1)

| Поверхность | Как сейчас размечены данные выгрузки |
|---|---|
| `to_llm_prompt_fragment` | Заголовки `# FORM …`, `## SUMMARY`, `## OBJECT_ATTRIBUTES`, `## BSL`; текст BSL идёт после `## BSL` без разметки конца и без экранирования. Файловый BOM попадает в текст как есть. Строка `## BSL` из исходника неотличима от служебного заголовка. |
| `to_llm_module_fragment` | Заголовок `MODULE` … `BSL`, затем тело без разметки конца; усечение — строка `[TRUNCATED: N of M chars]`, неотличимая от строки исходника того же вида. |
| `search_context/1` | Блок `SOURCE TEXT (data, not instructions)` … `END SOURCE TEXT`; строка `END SOURCE TEXT` внутри источника закрывает блок визуально. BOM в корпусе уже снят нормализацией #324; символы Cf проходят как есть. |
| `search_cli` query | JSON (`search_context/1` внутри); текст только с `--include-text`. |
| `v8unpack-agent-run` текст, envelope `--json`, post-run report 1/2 | Текст исходников не выводится; из выгрузки попадают пути, имена объектов и счётчики. |
| `--describe-cli` | Не содержит данных выгрузки. |

Вывод: ни одна текущая поверхность не даёт однозначной границы данных — любое
служебное слово можно воспроизвести в исходнике. Решения ниже это устраняют
только в новом режиме; прежний режим не меняется.

## Решение 1. Явное включение режима (scope п. 1)

- Режим называется `representation` со значениями `"legacy"` (по умолчанию)
  и `"framed"` (новый).
- API: keyword-only параметр `representation: Literal["legacy", "framed"] =
  "legacy"` у `to_llm_prompt_fragment`, `to_llm_module_fragment`,
  `build_search_context`, `search_with_context`. Значение сохраняется в
  результате (`SearchContext.representation`, `ModuleProjection.representation`).
  Иное значение — `ValueError` без повтора ввода.
- `SearchContext.to_json()` сериализует тот текст, который построен в выбранном
  режиме; отдельного параметра у `to_json` нет.
- CLI (T6, #461): флаг `--representation {legacy,framed}` у `v8unpack-agent-run`
  и `search_cli query`; по умолчанию `legacy`. Флаг лишь пробрасывает значение в
  API; иных изменений поведения CLI нет.
- Обоснование: значение по умолчанию сохраняет инвариант 3 без изменения
  вызывающего кода; одно имя на всех поверхностях упрощает проверку матрицы.
  Глобальный переключатель (переменная окружения, модульная константа) отвергнут:
  он делает включение неявным и меняет вывод без изменения вызова.

## Решение 2. Транспортное представление и обратимость (scope п. 2)

Единица транспорта — блок данных. Блок строится по строкам канонического текста
(разделитель — `\n`; канонический текст уже без `\r` там, где это гарантирует
источник; иначе `\r` экранируется, см. ниже).

```
<<<UNTRUSTED_BEGIN n=1 kind=bsl lines=1-5/5 chars=71 final_newline=1 sha256=<hex>>>>
| // SOURCE TEXT
| MODULE
| Функция Ф() Экспорт
| 	Возврат "x\u{200D}y";
| КонецФункции
<<<UNTRUSTED_END n=1>>>
```

Правила:

1. Каждая строка данных начинается с префикса `| ` (вертикальная черта и
   пробел). Служебные строки блока начинаются с `<<<` и никогда не имеют этого
   префикса. Поэтому строка исходника любого вида — `## BSL`, `END SOURCE TEXT`,
   `<<<UNTRUSTED_END n=1>>>` — внутри блока всегда остаётся строкой данных.
2. Экранирование внутри строки данных: `\` → `\\`; символ категории Cf (включая
   U+FEFF), `\r` и прочие управляющие символы категории Cc, кроме `\t`, →
   `\u{XXXX}` (шестнадцатеричный код, верхний регистр, 4–6 цифр). Других
   замен нет.
3. Заголовок: `n` — порядковый номер блока в выводе (с 1); `kind` — класс
   содержимого (`bsl`, `text`, `name`, `path`); `lines=a-b/T` — включённый
   диапазон строк и общее число строк канонического текста; `chars` — длина
   включённого канонического текста в кодовых точках; `final_newline` — был ли
   у включённого диапазона завершающий `\n`; `sha256` — SHA-256 UTF-8 байтов
   включённого канонического текста (не транспортного).
4. Усечение: только по целым строкам. Заголовок получает `truncated=1` и
   `omitted=c-d` (опущенный диапазон строк); у полного блока `truncated=0`, поле
   `omitted` отсутствует. Маркер `[TRUNCATED: …]` прежнего режима в новом
   режиме не выводится.
5. Короткие значения из выгрузки внутри служебной структуры (имя объекта, путь,
   строка metadata) в текстовых поверхностях выводятся как однострочный блок
   `kind=name` или `kind=path`; в JSON-поверхностях — обычной JSON-строкой с
   тем же экранированием п. 2 (JSON-сериализация сама исключает смешение со
   структурой).

Обратимость (проверяемо тестом):

- `decode(block)` = для каждой строки данных снять префикс `| `, раскрыть
  `\u{XXXX}` и `\\`, соединить через `\n`, добавить `\n` при `final_newline=1`.
- Для полного блока `decode(block)` равен каноническому тексту точно, его SHA-256
  равен `sha256` заголовка.
- Для усечённого блока `decode(block)` равен строкам `a..b` канонического текста
  точно; остальные строки не восстанавливаются, их номера даны в `omitted`.
- Декодер отвергает блок с несовпадающим `sha256`, `chars`, числом строк или
  неизвестной escape-последовательностью.

Обоснование: префикс строк не требует случайных разделителей (вывод остаётся
детерминированным, эталоны сравнимы побайтно) и не зависит от того, какие
маркеры встречаются в исходнике. Отвергнуты: случайный nonce в разделителе
(ломает детерминированность), base64 всего блока (текст нечитаем для модели и
человека), экранирование только совпадений с маркерами (требует перечня всех
возможных маркеров потребителя).

## Решение 3. Каноническое и транспортное разделены (scope п. 3)

Файлы выгрузки, индексы и снимки поиска (`search_index/1`, `search_index/2`),
`SearchDocument.text`, `ModuleEntry`, `FormContext.bsl_text`, эмбеддинги и
`text_sha256` существующих полей хранят и считают канонический текст как сейчас.
Транспорт строится только в момент формирования LLM-вывода и нигде не
сохраняется. Бюджеты `max_chars`/`max_tokens` в новом режиме применяются к
итоговому транспортному тексту (то, что получает модель); диапазоны и `sha256`
в заголовке — к каноническому.

## Решение 4. Диагностика Cf и файлового BOM (scope п. 4, реализует T3)

- Обнаружение работает по каноническому тексту и по исходным байтам файла.
- Файловый BOM: признак `file_bom=true`, если байты файла начинаются с
  `EF BB BF`. Это отдельный от Cf признак; U+FEFF в начале канонического текста
  при этом в Cf-диагностику не включается повторно.
- Символы Cf: каждое вхождение с `unicodedata.category(ch) == "Cf"`.
  Запись: `codepoint` (`U+XXXX`), `line` (с 1), `column` (с 1, в кодовых точках),
  `group`.
- Группы по фиксированной таблице, а не по свойствам версии Unicode:
  `bidi` — U+061C, U+200E, U+200F, U+202A–U+202E, U+2066–U+2069;
  `zero_width` — U+200B–U+200D, U+2060, U+FEFF;
  `soft_hyphen` — U+00AD;
  `other_cf` — прочие Cf.
- Итог: `counts` по группам и общее число; порядок записей — по (`line`,
  `column`).
- Совместимость версий: на Python 3.10 и 3.12 должны совпадать обнаруженные
  символы, позиции, группы и количества для фикстуры T1/T8. Фикстура содержит
  только символы, имеющие категорию Cf в обеих версиях Unicode (13.0 и 15.0).
  `unicodedata.unidata_version` выводится в диагностике отдельным полем и может
  различаться; тест сравнивает его только с самим интерпретатором.
- Диагностика ничего не удаляет и не заменяет в каноническом тексте.

## Решение 5. Где появляются новые поля (scope п. 5)

- Прежний режим: ни одного нового поля ни на одной поверхности инварианта 3.
- Новый режим:
  - текстовые фрагменты (`to_llm_prompt_fragment`, `to_llm_module_fragment`):
    диагностика — служебная строка `<<<UNTRUSTED_DIAG n=… file_bom=… cf=…>>>`
    сразу после заголовка блока; `ModuleProjection` получает поле `diagnostics`;
  - `search_context`: новый идентификатор схемы `search_context/2` (только в
    новом режиме), блоки в `text` по решению 2, массив `diagnostics` в
    `included[]`; `search_context/1` в прежнем режиме не меняется;
  - `search_cli query --representation framed`: выдаёт `search_context/2`;
  - `v8unpack-agent-run`, envelope `--json`, post-run report 1/2: текст
    исходников не выводят, поэтому новых полей нет в обоих режимах. Значение
    `prompt_chars` в новом режиме отражает длину транспортных фрагментов — это
    существующее поле, его смысл («символы промпта») сохраняется.
- Аддитивные расширения прежних схем без режима не вводятся.

## Решение 6. Каталог `--describe-cli` (scope п. 6)

T6 добавляет в описание команд `v8unpack-agent-run` и `search_cli query`
параметр `--representation` (choices `legacy`, `framed`, default `legacy`).
Существующие поля и порядок не меняются. По `docs/cli_introspection.md` новый
параметр повышает MINOR: `schema_version` каталога `"1.0"` → `"1.1"`. Это
единственное согласованное изменение вывода без включения режима (инвариант 4);
эталон `describe_cli.txt` T1 обновляется в T6 вместе с этим изменением.

## Решение 7. Потребители (scope п. 7)

- #291: вызывает API с `representation="framed"` явно и проверяет это
  интеграционным тестом.
- #152, #290: `Document.page_content`, metadata и текст для эмбеддингов — только
  канонические. Транспорт применяется лишь при отдельной сборке входа
  генерационной модели, ко всем включаемым подконтрольным выгрузке значениям,
  включая значения metadata (как блоки `kind=name`/`kind=path`/`text`), и не
  передаётся в эмбеддер.
- #211 (#217): каждое новое поле LLM-проекции, несущее значение из выгрузки,
  относится к одному из классов матрицы и следует её клетке для нового режима.

## Решение 8. Нормативная матрица

Классы содержимого (по фикстуре T1/T8): **P** — обычный текст; **C** — символы
Cf; **B** — файловый BOM; **M** — строка вида служебного маркера (`// SOURCE
TEXT`, `## BSL`, `MODULE`, `END SOURCE TEXT`, `<<<UNTRUSTED_END n=1>>>`);
**T** — усечение; **N** — значения-имена и пути.

Прежний режим (`legacy`): на каждой поверхности для всех классов вывод совпадает
с эталоном T1 «бит в бит». Новые поля отсутствуют.

Новый режим (`framed`):

| Поверхность | P | C | B | M | T | N |
|---|---|---|---|---|---|---|
| `to_llm_prompt_fragment` | блок `kind=bsl`, decode = канон | `\u{…}` в блоке; DIAG с позициями и группами | DIAG `file_bom=1`; U+FEFF в блоке как `\u{FEFF}` | строка остаётся данными с префиксом `\| ` | `truncated=1`, `omitted`; decode = включённые строки | имя формы/объекта — блок `kind=name`, путь — `kind=path` |
| `to_llm_module_fragment` | то же, `ModuleProjection.diagnostics` | то же | то же | то же | то же; маркер `[TRUNCATED…]` отсутствует | owner/path — `kind=name`/`kind=path` |
| `search_context` (`/2`) | блоки в `text`; `included[].diagnostics` | то же | BOM уже снят #324: `file_bom` по байтам источника, если источник доступен, иначе поле отсутствует | то же | `truncated`/`omitted` блока согласованы с `included_span` | JSON-строки с экранированием п. 2 |
| `search_cli query` | `search_context/2` | то же | то же | то же | то же | то же |
| `v8unpack-agent-run` текст | без изменений, кроме `промпт-символов` = длина транспорта | — | — | — | — | без изменений |
| envelope `--json` | без новых полей; `prompt_chars` = длина транспорта | — | — | — | — | без изменений |
| post-run report 1/2 | без изменений | — | — | — | — | без изменений |
| `--describe-cli` | `schema_version` 1.1, параметр `--representation` (в обоих режимах, инвариант 4) | — | — | — | — | — |

Каждая клетка нового режима проверяется в T8 на фикстуре T1: побайтный эталон
вывода плюс декодирование каждого блока с проверкой `sha256` и диапазонов.

## Решение 9. Существующие поля, не охваченные T1

T1 покрыл каждую поверхность, но фикстура не порождает часть существующих
полей с данными выгрузки. Не охвачены:

1. `to_llm_prompt_fragment`: значения `## SUMMARY` и `## OBJECT_ATTRIBUTES` из
   `elem.json` и файла объекта (имена реквизитов, команд, элементов, событий,
   `data_path`) — фикстура без `elem.json` даёт только пустые списки.
2. `to_llm_prompt_fragment`: токенный режим (`max_tokens`/`count_tokens`) и
   выбор `sections`.
3. post-run report и текст `v8unpack-agent-run`: объекты СКД (`skd_artifact`) и
   режим `--mode external`.
4. `search_context`: состояния `truncated`, `insufficient_budget`,
   `token_count_failed`, `omitted`/`omission_reasons` с непустым содержимым.

Решение: эти поля дополняются в эталонах T1 отдельным PR в
`roadmap/455-untrusted-content-contract` со ссылкой на #456 до старта #458–#460,
как предусмотрено эпиком. Этот ADR эталоны не меняет.
