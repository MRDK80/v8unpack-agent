# Размер снимка `search_index/1` и варианты хранения (#399)

Исследование эпика #398. Runtime, схемы и тесты не меняются: скрипт
[`scripts/measure_snapshot_size_issue399.py`](../../scripts/measure_snapshot_size_issue399.py)
строит снимки настоящими `IndexEntry`/`SearchIndex`, сохраняет и читает их
настоящими `save_index`/`load_index`, а варианты хранения собирает как
прототипы рядом во временном каталоге. Модель не загружается, сеть не
используется.

## Вопросы и краткие ответы

1. **Из чего состоит снимок.** Почти целиком из векторов, записанных текстом
   JSON. На пяти реальных выгрузках с `hashed-bow-demo` (256 изм.) —
   2,8–3,2 КБ на фрагмент: вектор — 61–64 %, описание артефакта, повторённое в
   каждом фрагменте, — 17–23 %, хеши — ~8 %, id и координаты — ~8 %.
   Составляющие сходятся с размером файла до байта. При 1024 измерениях
   плотного вектора вектор — ~95–97 %.
2. **BGE-M3 (1024 изм.) на ~323 тыс. фрагментов.** Не «в 4 раза больше», а
   примерно в 7 раз больше реального снимка крупной конфигурации (1,04 ГБ):
   плотный вектор float32, напечатанный как Python float, занимает ~21,7 КБ
   против ~1,9 КБ у `hashed-bow-demo`. Расчёт — **~7,4 ГБ** файла и
   **~26 ГБ** пика памяти при `load_index`.
3. **Варианты.** Отдельный двоичный файл векторов плюс словарь артефактов:
   на реальной крупной конфигурации (256 изм.) float32 — 505 МБ вместо
   1 036 МБ, загрузка 2,6 с вместо 59,9 с. Для 1024 изм. — ~1,5 ГБ (float32)
   или ~0,84 ГБ (float16) вместо ~7,4 ГБ; на синтетике 1024 изм. загрузка
   ускоряется ~в 100 раз, пик памяти падает ~в 12–18 раз.
4. **Загрузка и память.** Текущая загрузка — разбор всего JSON, пересчёт
   контрольной суммы по повторной сериализации и проверка каждого числа
   Python-кодом. На реальных данных 256 изм. — ~24 КБ памяти на фрагмент
   (tracemalloc), процесс замера крупной конфигурации достиг 14,8 ГБ RSS; при
   1024 изм. — ~80 КБ на фрагмент. Для крупной конфигурации с моделью 1024
   изм. текущий формат непригоден даже на машине с 32 ГБ.

## Методика

- Синтетика: артефакты-модули по 20 фрагментов, ASCII-имена, `TextSpan`,
  настоящие sha256 в hex. Два профиля векторов:
  - `sparse` — разреженный нормированный мешок слов, похож на
    `hashed-bow-demo`;
  - `dense` — нормированный гауссов вектор, прошедший через float32, как у
    моделей эмбеддингов.
- Составляющие считаются по полям записи в той же сериализации, что у снимка
  (`sort_keys`, компактные разделители, UTF-8). Массив записей независимо
  сериализуется целиком и сверяется с суммой полей; заголовок — разность с
  `to_json()`; итог сверяется с размером файла после `save_index`. Расхождение
  даёт RC=1.
- Варианты: метаданные — JSON с контрольной суммой, векторы — отдельный
  файл `float32`/`float16` (C-порядок) со своим sha256 в метаданных. Каждый
  вариант читается обратно; проверяются контрольные суммы, конечность и
  ненулевость векторов, число записей и форма матрицы.
- Время — `time.perf_counter` одного прогона на машине исследования (2 vCPU),
  пик памяти — `tracemalloc` при загрузке. Абсолютные секунды зависят от
  машины, соотношения переносимы.
- Совпадение ранжирования: 20 случайных запросов, top-10 по косинусу,
  float32/float16 против float64.

Воспроизведение (из корня клона, numpy нужен для двоичных вариантов):

```
PYTHONPATH=. python scripts/measure_snapshot_size_issue399.py --memory --ranking synthetic --scale 1600:256:sparse 10000:256:sparse 1600:1024:dense 10000:1024:dense
PYTHONPATH=. python scripts/measure_snapshot_size_issue399.py synthetic --scale 62000:256:sparse
```

Вывод — JSONL: по строке на масштаб и итоговая строка `summary` с
`status`, `import_blobs` (git blob SHA импортированных `search_index.py` и
`search_contract.py`) и `end`. Без строки `summary` результат неполный.
Использованные прогоны: скрипт v1, seed 399 (v2 отличается только обработкой
снимка без записей; повторный прогон v2 на 1 600 фрагментах дал те же числа), numpy 2.5.3, blob
`search_index.py` `e889bee4b59c7f35932493c86028c5ad1fa70e84`.

### Точность float16

Максимальная абсолютная ошибка компоненты нормированного вектора —
~6,1·10⁻⁵ (1024 изм.) и до ~1,7·10⁻⁴ (256 изм.). Совпадение top-10 с float64 на 20
случайных запросах: float32 — 20 из 20 по порядку во всех масштабах;
float16 — набор совпал во всех случаях, порядок — 20 из 20, кроме 10 000 ×
1024, где 19 из 20 (одна перестановка соседних позиций). Правило
`query_index` с равенством по `document_id` при float16 даёт больше ничьих;
для #406 это значит, что «результат идентичен» нужно сверять на float32 или
оговорить допуск.

## Влияние на целостность, свежесть и совместимость

- **Контрольная сумма.** Сейчас — sha256 от повторной сериализации всего тела;
  при отдельном файле векторов нужны два sha256 (метаданные и байты векторов)
  с перекрёстной ссылкой. Прототип хранит sha256 векторов в метаданных, и
  общая контрольная сумма метаданных его покрывает — подмена любого файла
  обнаруживается.
- **Проверка векторов.** Вместо поэлементной проверки Python — проверка
  матрицы numpy: конечность, ненулевые строки, форма `(n, dimension)`.
  Без numpy возможен медленный путь через `array`/`struct` из stdlib.
- **Свежесть.** Хеши и `document_id` остаются в метаданных — `assess` не
  меняется по смыслу. Словарь артефактов не влияет на свежесть.
- **Атомарность.** Два файла нельзя заменить одной операцией `os.replace`.
  Нужен порядок «векторы с уникальным именем → метаданные со ссылкой на него»
  либо каталог снимка с заменой целиком; при сбое между шагами старый снимок
  должен оставаться читаемым.
- **Совместимость.** Любой вариант — новая схема (`search_index/2`); `/1`
  остаётся читаемым. Решение о переходе — отдельная задача и решение
  владельца (инвариант эпика #398).
- **gzip.** На синтетике `sparse` сжатие нереалистично сильное: регулярные
  `0.0` и повторяющиеся описания. На плотных векторах — лишь ~2,3 раза при
  самом медленном сохранении. Двоичный float16 выигрывает и без сжатия.

## Ограничения

- Синтетика недооценивает реальный снимок с `hashed-bow-demo`: у владельца
  2,8–3,2 КБ на фрагмент против 1,8 КБ здесь — длиннее описания артефактов,
  пути и кириллические имена процедур (2 байта на символ в UTF-8). Замер
  владельца ниже это подтверждает: эффект словаря артефактов на реальных
  данных сильнее (`v4` — 0,49–0,57 размера против 0,77 на синтетике).
- Профиль `dense` моделирует длину записи числа, а не распределение
  настоящих эмбеддингов BGE-M3; размер двоичных вариантов от распределения
  не зависит, текстового JSON и gzip — зависит слабо.
- Совпадение ранжирования проверено на случайных векторах и запросах, а не на
  реальной выдаче; для решения о float16 нужна проверка на модели из #407.
- Время — один прогон на одной машине; пик памяти — `tracemalloc`, без
  накладных расходов интерпретатора вне отслеживаемых аллокаций.
- Экстраполяция на 323 тыс. — линейный расчёт по байтам на фрагмент;
  линейность подтверждена на 1,6–62 тыс. (256 изм.) и 1,6–10 тыс. (1024 изм.).

## Варианты для решения владельца

1. **`v5`: отдельный файл float16 + словарь артефактов** — наименьший размер
   и память без сжатия; цена — ошибка до ~2·10⁻⁴ и возможные перестановки равных
   оценок.
2. **`v4`: то же на float32** — ~1,5 ГБ для 323 тыс. × 1024 (505 МБ при
   256 изм. на реальной крупной конфигурации), без потери точности; результат
   ранжирования идентичен.
3. **Оставить `search_index/1`** только для `hashed-bow-demo` и малых
   конфигураций, а для моделей 1024 изм. ввести `/2` по варианту 1 или 2.

Рекомендация исследования — вариант 2 (`v4`, float32) как основной формат
`/2`: на реальных данных снимок вдвое меньше уже при 256 изм., при 1024 изм.
— ~в 5 раз; загрузка в 17–25 раз быстрее, память в ~6 раз меньше — без
изменения выдачи, что
согласуется с требованием #406 «результат идентичен»; float16 — опция после
проверки качества на модели (#407/#408). Реализация — отдельные задачи.
