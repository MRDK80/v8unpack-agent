# Авторитетные имена платформенных типов (issue #165)

Статус: research / evidence phase. Production-код этим отчётом не изменяется.

Документ фиксирует результат контролируемого эксперимента, связывающего
платформенные UUID из класса `reference_only` с каноническими машинными
именами типов. Отчёт закрывает вторую блокировку issue #165 — источник имён.
Первая блокировка (платформенная природа идентификаторов) закрыта в #164.

## 1. Постановка

По #164 доказана платформенная природа 14 UUID из 20 класса `reference_only`.
Совпадение идентификатора между независимыми конфигурациями доказывает
стабильность UUID, но не даёт человекочитаемого имени типа.

Требовался отдельный источник, связывающий конкретный UUID и каноническое имя
в одной доказательной цепочке. Готовой официальной таблицы найти не удалось,
поэтому применён экспериментальный маршрут: тип назначается **явно** в
минимальной синтетической конфигурации через штатный механизм выбора типа,
после чего экспортированный артефакт однозначно содержит его UUID.

Имя типа берётся не из названия реквизита и не из соседних признаков, а из
значения свойства «Тип», установленного официальной платформой.

## 2. Метод

### 2.1 Синтетическая конфигурация

Конфигурация содержит пять справочников без доменных имён. Каждый справочник
несёт ровно один изменяемый слот: либо реквизит формы, либо реквизит объекта.
Прогон меняет от одного до пяти слотов, после чего конфигурация выгружается
двумя независимыми каналами — в файл контейнера и в файлы XML.

Один слот на один справочник обязателен: при двух и более изменениях в одном
файле привязка «слот → UUID» становится неоднозначной. Именно такая
неоднозначность привела к одной ошибочной привязке на раннем этапе серии,
которая позже была отозвана и переделана изолированным прогоном.

### 2.2 Извлечение UUID

Носитель ссылки на тип в распакованном контейнере — блок следующего вида:

```text
[ "\"Pattern\"", [ "\"#\"", "<uuid>" ] ]
```

Блок располагается непосредственно после описания реквизита и работает
одинаково для реквизитов обычных форм и реквизитов объектов. Первое значение
в тройке описания реквизита — идентификатор самого реквизита, а не типа; их
смешение даёт ложные привязки.

Правило подтверждено контрольным наблюдением: для ссылок на объекты самой
конфигурации в том же блоке лежат константы, соответствующие типам
`CatalogRef.<имя>` из пакета `current-config`.

### 2.3 Извлечение имени

Каждая привязка подтверждается двумя независимыми каналами.

Первый канал — выгрузка в файлы XML, где для реквизита публикуется токен
`v8:Type` или `v8:TypeSet` с машинным именем типа.

Второй канал — фабрика XDTO платформы. Выгружен полный перечень пакетов и
типов фабрики, после чего имя проверено прямым вызовом сериализатора для
значения соответствующего типа.

### 2.4 Сверка дельты

Для каждого прогона снимается набор UUID до и после изменения, вычисляется
разность по файлам и сверяется с закрытым целевым набором. Дополнительно
фиксируются контрольные суммы исходных артефактов.

построителя отчёта.

## 4. Позиция без публикуемого имени

`0dda99d9-ae9f-43d2-b7ac-44f3fb0d4059` соответствует типу `ПостроительОтчета`.
UUID доказан изолированным слотом и воспроизведён в нескольких прогонах.
Машинного имени у типа нет: прямой вызов сериализатора вернул отсутствие имени
типа при четырёх успешных контрольных вызовах в том же цикле.

Контрольные вызовы того же цикла:

```text
ТаблицаЗначений                 -> http://v8.1c.ru/8.1/data/core | ValueTable
УникальныйИдентификатор         -> http://v8.1c.ru/8.1/data/core | UUID
ВидСравнения                    -> http://v8.1c.ru/8.1/data/enterprise | ComparisonType
ТипИзмеренияПостроителяОтчета   -> http://v8.1c.ru/8.3/data/entext | ReportBuilderDimensionType
ПостроительОтчета               -> имя отсутствует
```

Это измеренное свойство типа, а не пробел исследования: объект построителя
несёт внутреннее состояние и не имеет представления в схеме обмена. Полная
выгрузка фабрики XDTO подтверждает вывод косвенно — в пакете `entext` рядом с
типом измерения построителя нет типа самого построителя.

## 5. Расхождение подписи и идентификатора

Для одной позиции подпись в механизме выбора типа не совпадает с
идентификатором встроенного языка.

```text
подпись типа:              ПостроительОтчетаАнализаДанныхВидСравнения
идентификатор языка:       ВидСравнения
каноническое имя XDTO:     http://v8.1c.ru/8.1/data/enterprise | ComparisonType
```

Обращение по удлинённой подписи в коде не компилируется. Отсюда следует
методическое требование: сопоставлять типы по подписи интерфейса недостаточно,
каноническое имя проверяется через фабрику типов.

Различение этой позиции от смежной выполнено отдельным прогоном, где два слота
получили разные типы семейства построителя и дали разные UUID. Это же
наблюдение позволило отозвать более раннюю ошибочную привязку, полученную при
неоднозначном выборе типа в диалоге.

## 6. Воспроизводимость

Серия состоит из шестнадцати прогонов. Итоговые контрольные суммы двух
последних:

```text
прогон 15  контейнер  f9c2be3158ba3c1f9c768c92e6a1958ada1812dd7afce79539cd3732da6c421f
прогон 15  XML        341004dc90775d32521a95c995b8d746e49e864e9095fc353b3696be8f0ce303
прогон 16  контейнер  80a7f99dd3d02f6f533395c4abbe32f1f16ef7c9c3cd8e1057c704cc6692e593
прогон 16  XML        c1650dc95542528b53ddd4727c2c45490398681c779d479971a6b7bc074e788b
```

Базовая точка предыдущего прогона:

```text
прогон 14  контейнер  f92ca469f7efcd6dc980c35ccd48185bc229be1bd570bc6fe90d76881db5733e
```

Различие контрольных сумм соседних прогонов — обязательное условие: совпадение
означало бы, что изменение не сохранилось.

Порядок воспроизведения:

1. создать минимальную конфигурацию из пяти справочников без доменных имён;
2. назначить в каждом справочнике ровно один слот с явно выбранным типом;
3. выгрузить конфигурацию в контейнер и в файлы XML, снять контрольные суммы;
4. распаковать контейнер и собрать набор UUID;
5. вычислить разность с предыдущим прогоном по файлам;
6. прочитать блок `Pattern` для каждого изменённого слота;
7. сверить машинное имя с токеном `v8:Type` или `v8:TypeSet` в XML;
8. подтвердить имя через фабрику XDTO и вызов сериализатора.

## 7. Уровни объявления типа

Отдельным прогоном проверено, совпадают ли константы типов на уровне реквизита
формы и на уровне реквизита объекта. Четыре контрольных слота из четырёх
совпали с ранее доказанными значениями, поэтому результаты серии
распространяются на оба уровня объявления.

Имена реквизитов объекта публикуются в файле описания справочника, а не в файле
формы; для реквизитов обычных форм ссылка на тип остаётся в файле элементов
формы.

## 8. Границы доказательства

Доказано:

- платформенная природа идентификаторов — по #164;
- соответствие UUID и явно назначенного типа — контролируемыми прогонами;
- каноническое машинное имя для 13 из 14 целевых UUID — двумя независимыми
  каналами;
- отсутствие публикуемого имени для одной позиции — прямым измерением.

Не доказано и не утверждается:

- имена шести UUID, оставшихся только в одной конфигурации по #164;
- соответствие канонических имён локализованным подписям интерфейса;
- устойчивость имён на версиях платформы вне проверенной.

## 9. Обезличенность

В отчёте отсутствуют имена производственных конфигураций, объектов, форм и
реквизитов, абсолютные пути, хосты, строки подключения и содержимое
проприетарных артефактов.

Публикуемые UUID относятся только к платформенным константам, доказанным
в #164. Идентификаторы объектов конфигураций и позиции класса A-only не
публикуются. Производственные конфигурации обозначаются безлично; соответствие
обозначениям из #164 в этом документе не утверждается.

## 10. Следующий шаг

Отчёт закрывает research-фазу issue #165 и передаётся на evidence review.

Предмет решения координатора — вердикт по gate при результате 13 из 14 имён:
принимать его как PASS с документированным исключением либо сохранять BLOCKED
до появления имени для позиции без публикуемого представления.

При решении PASS реализация выполняется отдельно и включает статическую
таблицу, порядок резолюции `reference_types` → таблица → `Ref#uuid`,
синтетические тесты и замеры до/после. Настоящий документ production-код
не изменяет.

## Структура статической таблицы

Раздел фиксирует форму будущей константы и правила чтения её значений.
Решение принято по итогам research-фазы и заменяет предварительную оценку
«ровно 14 записей», сделанную до получения доказательств.

### 1. Тринадцать записей и явное множество исключений

```python
PLATFORM_REFERENCE_TYPES: dict[str, str] = {
    # 13 записей: UUID -> каноническое машинное имя типа
}

PLATFORM_TYPES_WITHOUT_XDTO_NAME: frozenset[str] = frozenset({
    "0dda99d9-ae9f-43d2-b7ac-44f3fb0d4059",  # тип без публикуемого имени
})
```

Второе множество не участвует в резолюции и существует только для
трассируемости и тестов. Проверка мощности двойная: 13 записей в словаре,
1 элемент в множестве исключений, пересечение пусто, сумма равна 14.

Смысл разделения — однородность значения. Все значения словаря принадлежат
одному классу: стабильное машинное имя из фабрики XDTO. Добавление
четырнадцатой записи с именем другого происхождения заставило бы каждого
потребителя таблицы знать правило нормализации, чтобы отличить один класс
имени от другого.

### 2. Признак Type или TypeSet по каждой позиции

Позиции выгружаются двумя разными токенами, и это различие внутри самих
тринадцати записей существеннее, чем отсутствующее имя у четырнадцатой.

| Класс значения | Токен выгрузки | Что означает |
|---|---|---|
| Конкретный платформенный тип | `v8:Type` | ровно один тип |
| Ссылочный набор объектов конфигурации | `v8:TypeSet` | множество однотипных ссылок |

Признак заполняется по фактическому токену, зафиксированному в журнале
контролируемых прогонов, а не по виду имени. Без этой пометки потребитель
таблицы не различит «ссылка на любой объект данного класса» и «конкретный
тип значения».

### 3. Правило записи значения

В таблице хранится префиксная форма `prefix:LocalName`, потому что именно
она встречается в XML-выгрузке. Префикс — соглашение сериализации, а не
часть имени типа: фабрика XDTO возвращает URI пространства имён и локальное
имя раздельно.

Соответствие префиксов и пространств имён приводится в журнале прогонов и
используется при любом сравнении значений с полной парой «URI + локальное
имя». Сравнение префиксной формы напрямую с URI некорректно.

Существующий `reference_types` использует стиль `CatalogRef.<Имя>` для
объектов конфигурации. Значения статической таблицы к этому стилю не
приводятся и не смешиваются с ним: первая ступень резолюции всегда
приоритетнее статической таблицы.

### 4. Обоснование исключения

Для `0dda99d9-ae9f-43d2-b7ac-44f3fb0d4059` отсутствие публикуемого имени —
результат прямого измерения, а не пробел поиска. В одном цикле вызовов
сериализатор вернул отсутствие имени для этого типа при четырёх успешных
контрольных вызовах для других значений, включая два контроля из
пространства `data/core`.

Отсутствие ключа в таблице даёт уже задокументированное и покрытое тестами
поведение: `None` от резолвера и `Ref#uuid` от декодера. UUID при этом не
теряется, а фактический прирост coverage оказывается ниже потолка на долю
вхождений этой позиции.

### Побочное наблюдение вне целевого набора

`e72fe022-682f-445d-bba5-3bbd9ff02242` подтверждён контролируемым слотом как
отдельный тип механизма анализа данных. В целевой набор он не входит, его
каноническое имя не проверялось, и он не включается ни в статическую
таблицу, ни во множество исключений.

## Дополнение по запросу evidence review

Блок отвечает на четыре уточнения координатора: среда измерений, место
хранения признака токена, пересчитанный ожидаемый эффект и уточнённый
контракт будущей константы.

### 1. Среда измерений

Все контролируемые прогоны выполнены в одной среде.

| Параметр | Значение |
|---|---|
| Версия платформы | 8.3.27.2214 |
| Версия ОС | Linux 7.0.0-31-generic, Ubuntu 24.04, SMP PREEMPT_DYNAMIC |
| Вариант встроенного языка конфигурации | Русский |
| Код локализации информационной базы | `ru_RU` |
| Текущий код локализации сеанса | `ru` |
| Текущий язык | Русский |
| Язык системы | `ru` |
| Режим запуска | толстый клиент, обычное приложение |

Два следствия для границы доказательства.

Воспроизведение на второй версии платформы не выполнялось: серия измерений
опирается на одну версию и два независимых канала подтверждения имени —
токен выгрузки XML и фабрику XDTO. Это осознанное ограничение, а не пробел
методики; при появлении второй доступной версии сверку следует повторить.

Код локализации базы и код локализации сеанса различаются: `ru_RU` против
`ru`. Именно поэтому подпись типа в механизме выбора отображалась
по-русски, и именно поэтому локализованная подпись не может служить
каноническим именем.

### 2. Где хранится признак Type или TypeSet

Решение: признак хранится **только в research-отчёте**, в составе
доказательной таблицы. В production-константу он не выносится.

Обоснование:

- контракт резолвера отвечает на один вопрос — какое имя соответствует
  UUID; `dict[str, str]` этого достаточно;
- признак нужен читателю доказательств, чтобы не спутать ссылочный набор
  объектов конфигурации с конкретным типом значения, а не рантайму;
- добавление второго поля превратило бы константу в структуру, потребовало
  бы решения о формате и теста согласованности ради данных, которые ни один
  потребитель не запрашивает.

Если признак понадобится коду позднее, корректное место — отдельная
константа рядом с таблицей, по образцу множества исключений, оформленная
отдельной задачей вместе с потребителем. Колонка внутри mapping не
рассматривается.

### 3. Вхождения позиции без имени и пересчитанный эффект

Выполнен точный прогон диагностики методики #143/#164 на выгрузке A публичным
примером `examples/unresolved_refs_report.py`. Два независимых прогона дали
побайтово идентичный вывод, RC=0.

#### Отождествление строки отчёта

Отчёт публикует UUID обезличенно, поэтому строка остатка отождествлена по
колонке «позиций», которая воспроизводится независимым текстовым поиском:

| Строка отчёта | Вхождений | Позиций | Текстовый поиск по UUID |
|---|---:|---:|---:|
| U03 | 83 | 1 463 | 1 463 — совпало |
| U04 | 81 | 69 | 69 — совпало |

Два совпадения на разных порядках величин и проверка уникальности значения
«позиций 69» — оно встречается в отчёте ровно один раз — делают отождествление
однозначным. Позиция без публикуемого имени соответствует строке U04.

#### Две метрики и их различие

| Метрика | Значение | Что считает |
|---|---:|---|
| `resolver_occurrences` | **81** | ссылочные грани реквизитов, разрешаемые резолвером |
| `raw_positions` | 69 | текстовые позиции UUID в файлах распакованной выгрузки |

Вхождений больше, чем позиций, потому что одна позиция определения типа
адресуется несколькими гранями реквизитов в разных формах. По отчёту U04
распределён на 42 формы обработок и 39 форм отчётов, доля в остатке — 6.23 %.

`raw_positions` остаётся диагностической метрикой: она удобна для быстрой
локализации файлов, но в расчёт coverage не подставляется. Ранее приведённая
оценка через коэффициент 0,81 снята: она опиралась на непроверенное значение,
которого в фактическом отчёте нет.

#### Точный пересчёт

| Величина | Значение |
|---|---:|
| Применимых ссылочных вхождений | 15 723 |
| Resolved до | 14 422 (91.7255 %) |
| Потолок доказанного объёма, 14 UUID | 1 107 |
| Вхождений позиции без имени | 81 |
| Новых резолюций для 13 записей | **1 026** |
| Итоговое resolved | **15 448** |
| Остаток `reference_only` | **117** |
| Остаток unresolved всего | **275** |
| Coverage после | **98.2510 %** |
| Дельта | **+6.5255 п.п.** |

#### Проверки сходимости

Две независимые тождественности подтверждают расчёт:

```text
1143 - 1026 = 117
  36 +   81 = 117      A-only вхождения плюс позиция без имени

1301 - 1026 = 275
 117 +  158 = 275      остаток reference_only плюс нессылочные классы
```

Ни одна величина не подгонялась под ожидание. Значения `resolved = 14422`,
`unresolved = 1301`, `applicable_reference_occurrences = 15723` и
`in_index_but_unresolved = 0` взяты из шапки того же прогона.

#### Отношение к вердикту confirmed_two_configs

Текстовое присутствие UUID в третьей выгрузке — одна позиция — не равно
resolver-level подтверждению: одиночная текстовая позиция не порождает
ссылочной грани реквизита. Вердикт `confirmed_two_configs` по #164 считался
по граням, поэтому расхождение с текстовой метрикой ожидаемо и классификацию
не меняет.

### 4. Уточнённый контракт константы

Против исходной постановки контракт меняется: вместо словаря на
четырнадцать записей — тринадцать записей отображения и один явный
fallback.

```python
PLATFORM_REFERENCE_TYPES: dict[str, str]          # 13 записей
PLATFORM_TYPES_WITHOUT_XDTO_NAME: frozenset[str]  # 1 UUID, вне резолюции
```

Правила:

- инвариант `13 + 1 = 14`, пересечение множеств пусто;
- для UUID из множества исключений резолвер возвращает `None`, а декодер
  сохраняет `Ref#uuid`; это явный документированный fallback, а не пробел
  доказательства;
- значение таблицы — стабильное машинное имя из фабрики XDTO в префиксной
  форме `prefix:LocalName`;
- порядок резолюции `reference_types` → таблица платформенных типов →
  `Ref#uuid`; первая ступень приоритетнее, непустое пересечение ключей
  с индексом считается ошибкой таблицы;
- шесть UUID, подтверждённых только в одной выгрузке, и побочные
  наблюдения вне целевого набора в обе константы не входят.

Причина разделения — однородность значения. Все значения словаря
принадлежат одному классу имени; запись другого происхождения заставила бы
каждого потребителя знать правило нормализации, чтобы отличить один класс
от другого.
