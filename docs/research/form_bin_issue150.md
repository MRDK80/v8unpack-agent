# Исследование #150: обычные формы с бинарным макетом `Form.bin`

Дата: 6 сентября 2026. Базовый коммит: `218f857`. Ветка: `research/150-form-bin-validation`.

Production-код в рамках этого исследования не изменялся.

## Scope and evidence

Задача исследовательская: проверить гипотезу внешнего review о том, что обычные
(неуправляемые) формы с бинарным макетом `Form.bin` распаковываются неполно и из-за
этого попадают в `unknown` или получают `elem_index_ok=False`.

Evidence gate пройден. В трёх независимых выгрузках найдено 4782 реальных `Form.bin`:

| Конфигурация | Реальных `Form.bin` | min / median / max, байт |
|---|---:|---|
| A | 1354 | 2473 / 21745 / 2353626 |
| B | 6 | 4029 / 89401 / 113529 |
| C | 3422 | 2473 / 47558 / 4555492 |

Важная поправка к предыдущим материалам: ранее по конфигурации C фиксировалось
`Form.bin: 0 файлов` и статус `not applicable for C`. Этот вывод опровергнут. Ноль был
артефактом режима выгрузки: в выгрузках, сделанных иначе, `Form.bin` отсутствует, а в
выгрузке конфигурации в файлы тех же конфигураций он присутствует массово.

Синтетические `Form.bin` из `tests/` и `examples/` в выборку не включались: скрипты
инвентаризации отказываются сканировать каталоги внутри рабочего дерева репозитория.

## Sample methodology

- Инвентаризация: рекурсивный поиск файлов с именем `Form.bin` по разрешённым локальным
  корням выгрузок; публикуются только агрегаты, псевдонимы конфигураций A/B/C и образцов
  `S001…`, короткие sha256-отпечатки.
- Стратификация: семь корзин по размеру (`0–5000`, `5000–10000`, `10000–25000`,
  `25000–50000`, `50000–100000`, `100000–500000`, `500000+`) и топология каталога формы.
- Отбор детерминированный: сортировка по корзине, размеру и sha256 от имени, а не по
  порядку файловой системы.
- Прогоны выполнялись на конфигурации C как самой представительной: 3422 файла.
- Все тексты ошибок и предупреждений проходят через редактор путей: токены со слешем
  заменяются на `<path>`.

## Pipeline stages

Фактическая цепочка по установленному коду отличается от первоначальной формулировки
issue. В upstream `v8unpack` 1.2.11 нет функции `extract_str`; публичная точка входа —
`extract(in_filename, out_dir_name, *, temp_dir, index, processes, options)`, внутри неё
стадии `container_extract` → `decompress_and_extract` → `decode` → организация файлов.

В самом репозитории стадия «`Form.bin` → текстовый слой» не реализована. Она
делегируется вызывающей стороне: `FormUnpacker = Callable[[Path, Path, str],
FormArtifact]`, вызов `unpacker(bin_path, unpacked_root, name)` в `unpack_all_forms`.
В `examples/basic_usage.py` используется `demo_unpacker` — заглушка, в
`tests/test_pipeline.py` — `_fake_unpacker` и `partial_unpacker`. Production-модули,
включая `runner.py`, upstream для форм не вызывают.

Следствие: гипотезу о неполной распаковке нельзя отнести к коду этого репозитория без
явного адаптера. Для исследования адаптер был собран локально, вне репозитория, и
делегировал распаковку в upstream.

## Aggregated results

Бухгалтерия обнаружения на конфигурации C:

| Показатель | Значение |
|---|---:|
| Реальных `Form.bin` на диске | 3422 |
| Соответствуют конвенции `.../Forms/<Имя>/Ext/Form.bin` | 3357 |
| Вне конвенции (все — общие формы) | 65 |
| Уникальных имён форм внутри конвенции | 535 |
| Возвращает `discover_form_bins` | 535 |
| Потеряно на перезаписи словаря по имени | 2822 |
| Имён, используемых более одним объектом | 111 |
| Максимум повторов одного имени | 458 |

Гистограмма повторного использования имён: 424 имени встречаются один раз, далее
разреженный хвост, отдельные имена встречаются 155, 220, 361 и 458 раз.

Локализация стадий на 14 стратифицированных образцах (по два на непустую корзину):

| Стадия | Результат |
|---|---|
| Заголовок входа | `ffffff7f000200000200000000000000` у всех 14 образцов |
| `container_extract` | успешно у 14/14, ровно 2 внутренних элемента без расширений |
| `decompress_and_extract` | отказ у 14/14, `Error -3 while decompressing data: invalid block type` |
| `decode` | не достигнут ни разу |
| Текстовый слой | не создан |
| `parse_elem_json` | на реальных данных не выполнялся |

Размер образца на результат не влияет: отказ одинаков от 2473 до 504679 байт.

## Failure classes

1. `discovery_name_collision` — `discover_form_bins` возвращает `dict[str, Path]` с ключом
   по имени формы без владельца, поэтому одноимённые формы разных объектов метаданных
   молча перезаписывают друг друга. Потеря 2822 файла из 3357.
2. `discovery_off_convention` — 65 файлов общих форм не попадают в результат, потому что в
   их пути отсутствует сегмент `Forms`.
3. `missing_form_unpacker` — в репозитории нет production-адаптера `Form.bin`; контракт
   инъектируемого `FormUnpacker` осознанный, но документация упоминает функцию `index_cf()`,
   которой в `pipeline` нет.
4. `upstream_decompress_unsupported` — upstream распознаёт контейнер формы, но безусловное
   разжатие внутренних элементов `form` и `module` завершается ошибкой на всех образцах.
5. `unknown_share_unmeasured` — доля `unknown` и `elem_index_ok=False` по обычным формам не
   измерена, поскольку текстовый слой не получен.

## Upstream boundary

Первая стадия расхождения находится в upstream: `container_extract` проходит,
`decompress_and_extract` — нет. Документированные входы upstream — `cf`, `cfe`, `epf`;
одиночный `Form.bin` из выгрузки конфигурации в файлы в этот перечень не входит. Поэтому
корректная формулировка для upstream — не дефект, а отсутствие поддержки сценария, и
заводить её следует после проверки штатного входа `.cf` на том же наборе данных.

Исправление upstream внутри этого репозитория не выполняется.

## Decision matrix

| Класс | Решение | Обоснование |
|---|---|---|
| `discovery_name_collision` | implement | Доказанная потеря 2822 из 3357 файлов внутри этого репозитория; требует изменения публичного контракта, поэтому выносится в отдельную implementation issue |
| `discovery_off_convention` | implement | 65 общих форм не обнаруживаются; тот же контракт |
| `missing_form_unpacker` | keep as is + docs | Инъекция распаковщика — сознательное решение; правки требует только документация |
| `upstream_decompress_unsupported` | upstream issue | 14/14 отказов на однородном входе; заводится после проверки `.cf` |
| `unknown_share_unmeasured` | insufficient evidence | Стадия парсинга не достигнута; гипотеза о доле `unknown` не подтверждена и не опровергнута |

## Limitations

- Прогон стадий выполнен только на конфигурации C; A и B инвентаризованы, но не прогонялись.
- Выборка стадий — 14 образцов, по два на непустую корзину размеров.
- Штатный вход upstream `.cf` на этих данных ещё не проверен, поэтому класс
  `upstream_decompress_unsupported` зафиксирован как граница, а не как оформленный дефект.
- Локальный адаптер вызывал внутренние стадии upstream напрямую; результат штатного вызова
  `extract` с параметром `options` не исследовался.
- Детерминированность: два независимых прогона дали идентичные агрегаты обнаружения и
  идентичную первую падающую стадию у всех 14 образцов. Различается только имя внутреннего
  элемента, попавшего в текст ошибки (`form` либо `module`): порядок определяется
  планированием пула процессов upstream. Содержательные расхождения отсутствуют.

## Conclusion

Гипотеза внешнего review подтверждена частично и в другом месте, чем предполагалось.
Проблема обычных форм с бинарным макетом существует, но её первая и самая крупная часть
находится не в парсинге, а в обнаружении: `discover_form_bins` теряет 84,4 % реальных
`Form.bin` — 2822 файла на коллизиях имён и 65 общих форм вне конвенции путей.

Вторая часть лежит на границе upstream: одиночный `Form.bin` из выгрузки конфигурации в
файлы не разжимается `v8unpack` 1.2.11 на всех проверенных образцах, поэтому текстовый
слой не создаётся и `parse_elem_json` не достигается.

Утверждение о влиянии обычных форм на долю `unknown` остаётся недоказанным: измерить её
без текстового слоя невозможно. Implementation issue по обнаружению создаётся отдельно,
упstream-обращение — после проверки штатного входа `.cf`.
