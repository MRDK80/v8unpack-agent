# #212 — итог исследования динамических операций управляемых форм

Исследовательский отчёт по четырём конфигурациям. Расширение MVP принято владельцем в обсуждении. Закрытие задачи выполняется отдельно после обязательных проверок. Production-код и публичные API в #212 не менялись; модели не запускались.

Исследование выполнено на зафиксированном main `85d0d37ae5740601bb45f31f940ad9de486121d3` (0.4.0). Это основание эксперимента, а не утверждение о текущем HEAD GitHub. Версия исходного широкого пробника сохранялась при добавлении C4. Пробник не является реализацией будущего MVP.

Единица — синтаксическое место операции в модуле конкретной формы. Каждое присваивание учитывается отдельно; цикл даёт одно место-шаблон; batch изменения реквизитов — один вызов с отдельным указанием списков добавления/удаления. Вызовы helper не умножают операции тела. Передача формы в вызов сама по себе не доказывает её изменение. Повторяющиеся модули в разных формах остаются отдельными местами; это не независимые наблюдения качества.

Четыре входа имеют разные корневые идентичности конфигурации и файла. Признаков повторной выгрузки одного входа или пары «основная конфигурация / расширение» по доступным данным не обнаружено. Полная генеалогия поставок не проверялась. Пересечения уникальных байтовых хешей модулей форм: C1/C2 — 148, C1/C3 — 1, C2/C3 — 1; C4 с C1/C2/C3 — 12/3/0. Число уникальных хешей: 1 731 / 3 305 / 56 / 5 513. Корпус пригоден для исследования четырёх конфигураций, но полной статистической независимости исходников и конструкций не заявляем.

Managed marker — эмпирический признак, не доказательство полноты discovery управляемых форм. Контрольные группы не смешаны с основным знаменателем:

- C1–C3: просмотрены 685 кандидатов; 640 вне основного scope, 18 с неопределённым layout, 14 отклонены; полным чтением трёх дополнительных модулей подтверждены 13 операций управляемых форм без marker.
- C4: просмотрены 111 кандидатов в контрольных модулях неизвестного layout; 107 имеют подтверждённую UI-семантику операции, 3 unresolved, 1 отклонён. Тип всех 57 контрольных модулей с BSL не установлен.
- В C1–C3 ordinary-marker контроль выборочный (30/30/6 модулей), unknown-layout контроль полный на уровне пробника. В C4 пробник обработал все формы с BSL всех layout. Протоколы контроля и знаменатели различаются.

Всего индивидуально просмотрены 94 948 основных и 796 контрольных кандидатов; непроверенного остатка кандидатов нет. Это не сплошное чтение всех модулей и не доказательство общекорпусной полноты.

Замороженный MVP v1 сохраняется неизменным для сравнения; принятое расширение обозначается v2.

Сопоставление регистронезависимое, RU/EN соответствия должны быть проверены по платформенному контракту. Любой setter требует доказанного получателя; совпадения имени свойства недостаточно.

Для #213 закрепить схему: вид операции и цели, происхождение цели, свойство, диапазон исходника, процедура, аргументы, статусы каждого поля и операции, условия и provenance, наличие списков batch-вызова. `exact` требует доказанной операции, получателя и обязательных полей; `partial` сохраняет доказанную операцию с неполными полями; `unresolved` явно сообщает недостаток доказательств. Статический exact не обещает выполнение операции. Согласованное правило #213: ссылка на результат доказанного создания элемента — exact, даже если его имя вычисляется. Статус имени хранится отдельно. Setter с такой ссылкой и точным значением может быть exact; partial создающей операции автоматически на setter не переносится. Условия имеют отдельные expression_resolution (exact при полном извлечении) и runtime_truth = unknown. Exact-ссылка на условно созданный элемент действует в доказанном контексте ветви (valid_in); за пределы ветви автоматически не переносится.

Для #214: прямые доказанные коллекции формы и метод изменения реквизитов; проверка сигнатур, затенения, областей видимости и различение присваивания/сравнения. Вычисляемое имя не препятствует обнаружению доказанной операции. Условия `unconditional`, `if`, `loop`, `preprocessor`, `mixed`, `unknown` отражаются отдельно; обе ветви препроцессора сохраняются без выбора активной.

Для #215: локальные псевдонимы созданных/найденных элементов, setter-цепочки, связи с объявленными целями, родителем и путём данных; инвалидация при переназначении. Вложенный объект данных не становится UI-элементом только потому, что достижим через коллекцию формы.

## Ошибки и ограничения оценки

Полностью прочитан 31 модуль: 23 в C1–C3 и 8 в C4. Модули выбирались до чтения по фиксированному SHA-256 ранжированию с seed `212-gold-20261118`: по два из слоёв positive/broad_only/zero, плюс дополнительные отказы строгого лексера. Малые/пустые слои учитывались явно. При чтении список кандидатов не показывался. Разметку выполнял один ассистент; независимого человеческого или второго экспертного ревью и измерения согласия нет.

| Корпус | Операций gold | Широкий пробник TP/FP/FN | Фильтр получателя TP/FP/FN |
|---|---:|---:|---:|
| C1 | 91 | 88 / 0 / 3 | 75 / 0 / 16 |
| C2 | 34 | 30 / 4 / 4 | 19 / 0 / 15 |
| C3 | 194 | 187 / 6 / 7 | 181 / 3 / 13 |
| C4 | 101 | 101 / 0 / 0 | 96 / 0 / 5 |
| Сумма, без весов | 420 | 406 / 10 / 14 | 371 / 3 / 49 |

У широкого пробника на этих модулях precision 97,60%, recall 96,67%; у фильтра получателя — 99,20% и 88,33%. Это описательная сумма выбранных модулей, не популяционная оценка. Оценки с весами N/n хранятся отдельно; два модуля на слой дают высокую чувствительность к выбору, интервальная гарантия не заявляется. Дополнительные lexer-failure модули не удваивают веса основных слоёв.

В C4 из 101 gold-операции 65 входят в закрытый scope MVP, 36 намеренно вне него. Фильтр внутри scope дал 60 TP, 0 FP, 5 FN; recall 92,31%. Пять пропусков включают прямые свойства формы, локальный псевдоним и вложенную UI-цепочку. Их нельзя целиком приписать будущему #216. Scope-фильтр не реализует #214/#215. Precision/recall будущего MVP ещё не измерены.

Ложные совпадения включают диалоги, сообщения пользователю, структуры, области табличных документов и одноимённые коллекции данных. Сплошной просмотр кандидатов оценивает найденные места; поиск FN требует полного чтения модулей, включая zero и lexer-failure. Unknown не считается ни TP, ни FP.

## Пригодность bsl_facts для #214

Переиспользуемы лексические примитивы: границы токенов, исключение комментариев, атомарные строки, позиции и casefold-сопоставление. Приватные `_tokens`/`_Token` не являются готовым публичным API детектора, а декларационный анализ имеет более узкий контракт.

Строгий лексер отказал в 86/1 109 основных модулей C1–C3 и 523/5 903 C4, всего 609/7 012. Причины C4: условные/неизвестные директивы — 491, литерал даты — 15, продолжение строки — 7, неподдержанный символ — 10. Допускающий исследовательский обход не подтверждает компилируемость BSL. В #214 нельзя молча ослабить действующий контракт bsl_facts или превратить отказ в пустой полный результат; нужны явные unsupported/incomplete и отдельный контракт обхода директив.

## Критерии замеров #216

Решение по #216 остаётся открытым. Основное сравнение — законченные #214+#215 (A) против той же версии с ограниченным локальным data flow (B). Новый алгоритм не должен расширять список операций/свойств во время измерения: иначе прирост scope смешается с приростом анализа.

Протокол замеров:

1. Зафиксировать SHA A/B, окружение, манифесты входов и разметки; одинаковые настройки, порядок и scope v2. Запустить A и B по два раза в свежих процессах, проверить идентичность канонических результатов каждой версии. Время, peak RSS и таймауты измерить отдельно по каждой конфигурации и суммарно; нельзя переносить нынешние времена пробника на A/B.
2. Использовать C1–C4 как раскрытый исследовательский/регрессионный корпус. До настройки B зафиксировать дополнительные полностью читаемые модули, ещё не использованные для настройки: основные слои positive/broad_only/zero и отказы лексера. Отдельно сформировать диагностический слой unresolved, не смешивая его с оценкой частот всего корпуса. Если независимых модулей нет, прямо обозначить оценку как регрессионную.
3. Сопоставлять места по виду и диапазону, отдельно проверять дубли. Сплошь разобрать все различия A/B; прирост TP засчитывать только после проверки реальности получателя и операции. Разрешённый получатель, восстановленное поле и новая найденная операция — три разных результата. Переход exact/partial сам по себе не новый TP.
4. Для каждой C1–C4 показать TP/FP/FN, precision/recall внутри scope; ΔTP, ΔFP, ΔFN, новые FP и потери ранее верных TP отдельно. За пределами scope вести отдельную опись. Для unresolved публиковать переходы operation/reject/still_unresolved и причины. Число сниженных unknown без gold-проверки не метрика качества.
5. Отдельно сравнить ложное подтверждение получателя, target/parent/data-path связи и статусы полей. Проверить отрицательные случаи: затенение, переназначение, конфликт ветвей, циклы, смешанные определения, вложенные объекты данных; проверить детерминизм и сохранность provenance/условий.
6. Показать распределение выигрыша по конфигурациям, уникальным хешам модулей и семействам повторов. Один многократно скопированный шаблон не должен создавать видимость широкого улучшения. Дать микроагрегат и невзвешенное среднее по конфигурациям, а также исходные знаменатели.

Инженерные пороги решения **приняты владельцем до реализации/настройки B**. Они не являются статистическими гарантиями:

- значимый выигрыш: устранить не менее 20% FN версии A внутри scope на полной проверочной разметке и подтвердить не менее 20 дополнительных TP суммарно, с выигрышем минимум в двух конфигурациях; отдельно показать выигрыш без байтовых повторов;
- ограничение качества: точность B не ниже A более чем на 0,5 процентного пункта по совокупности, без необъяснённой регрессии по отдельной конфигурации; все новые FP и утраченные TP разобраны. Из-за малого gold это инженерные пороги, не статистическое доказательство неухудшения;
- ограничение стоимости: время полного прохода и peak RSS B не более 2× A в том же окружении, без новых таймаутов и потери детерминизма; при превышении — отдельное решение по конкретной цене и пользе;
- если FN A слишком мало для содержательного порога, проверочную разметку расширить до оценки B либо оставить решение неопределённым. Нулевой/малый знаменатель не превращать в положительный результат;
- если прирост мал или ограничен повторяющимся шаблоном, предложить перенос #216 из основного пути и переход к #217 после #215. Изменение графа и текста эпика требует отдельного согласования и записи в GitHub.

## Повторяемость, #217 и #218

Для C1–C3 два последовательных свежих процесса обработали все три входа: 11,681 и 11,889 с за весь набор. Отдельные времена C1/C2/C3 не измерялись. C4: 97,393 и 96,821 с. Манифесты входов проверены после прогонов; C4 дополнительно проверен после разметки (78 621 BSL/JSON-файл без изменений). Кроссплатформенная повторяемость и peak RSS нынешнего пробника не измерены.

Будущий #217 использует `framed`-контракт после #455: канонические факты отдельно от транспорта, полный блок операции со статусом и provenance, бюджет по транспортному тексту, проверки round-trip/marker/Cf/truncation. Реальные значения из выгрузки остаются недоверенными данными.

Для #218 сохраняются корпус, манифесты, все аннотации, оба прогона и синтетические примеры. C4 после обсуждения и расширения MVP стал исследовательским/регрессионным корпусом; независимой финальной оценкой настроенного на нём детектора он больше не служит.

Результат #212 — исследовательское обоснование модели и границ MVP, а не готовый production-детектор. В этом отчёте только обезличенные агрегаты и платформенные термины; реальные имена, пути, литералы, фрагменты и нормализованные производные BSL остаются в приватных локальных материалах. Следующий шаг по зависимостям — #213.
