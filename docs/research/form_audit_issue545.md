# Почему 17 форм остались без статической описи (#545)

База — `95a29889e45fdea90170f61c1f5af11424e04dbc`. Сравнение на A/B/C
выполнено при аудиторском лимите 10 МБ на файл, как в #539. Все 5959 полных
отчётов совпали по хэшу упорядоченного списка. Формы `0-5-1` относятся
к [#541](form_help_issue541.md).

после разбора JSON при подсчёте узлов элементного артефакта.

## Корни, пропущенные при распаковке

У записей 1–4 из A оба члена формы присутствовали в исходном CF.
Под Linux и v8unpack 1.2.13 подтвердилось расхождение регистра UUID
в заголовке и имени члена. Путь с исходным регистром заголовка
не существует. Нижний регистр ведёт к каталогу `.0` с `form` и
`module` и к файлу `.1`. При обычном прогоне корень уже отсутствовал
сразу после `FormCore.decode_includes`, до записи JSON. Это дефект
поиска в распаковщике.

Локальная коррекция применена только к выбранным UUID в новой выгрузке.
[Скрипт повтора](../../scripts/reextract_form_roots_issue545.py)
использует нижний регистр при отсутствии обоих точных путей и наличии
каталога с исходным `form`. UUID объекта сохраняется. Скрипт требует
новый выходной каталог и приватный JSON-массив UUID. Функция действует
только в процессе этого прогона.

| Анонимный номер | Корень исходного CF | Статус исходной выгрузки | Статус после повторной распаковки | Имен |
| --- | --- | --- | --- | ---: |
| 1 | 19/16 | raw_form_unavailable | complete | 1 |
| 2 | 19/16 | raw_form_unavailable | complete | 1 |
| 3 | 19/16 | raw_form_unavailable | complete | 2 |
| 4 | 19/16 | raw_form_unavailable | complete | 2 |

Для всех четырёх эталон извлечён непосредственно из счётчика и
пятиэлементных записей brace-файла `.0/form` до организованной распаковки.
Хэши упорядоченных имён совпали с отчётами анализатора новой выгрузки.

На исходных A/B/C при пределе 200 000 узлов подтверждены 5959 из 6030.
В той же выборке после локальной коррекции четырёх входов подтверждены
ещё четыре описи. Для проверки 13 крупных документов отдельно поднят
аудиторский предел узлов до 400 000 при тех же 10 МБ на файл, см. ниже.
Ни UUID, ни сырой текст рабочих выгрузок в отчёт не входят.

## Повтор и границы прироста

Исходный аудит на A/B/C даёт 5959/6030 при неизменённом лимите
узлов. Замена только четырёх подтверждённых входных пар результатами
повторной распаковки даёт 5963/6030. Полная свежая распаковка исходного
CF для A обнаружила 2212 записей, поэтому её знаменатель отдельно
от исходных 2216. В расчёт прироста вошли только четыре проверенные
по UUID пары.

В контрольном прогоне на исходной C с лимитом 400 000 узлов все
13 отчётов совпали с именами из raw и сохранили порядок. Прежние
отчёты C совпали по приватной квитанции. При обеих локальных поправках
суммарный результат для исходной выборки составляет 5976/6030.
Это отдельный контроль. В штатной политике лимит 200 000 сохранён,
а обычная распаковка через upstream требует исправления поиска UUID.

Для повторения используйте аудит с ограничением байтов из
[приёмки #539](form_coverage_issue539.md). Для отдельного контроля
увеличьте `form_evidence.MAX_DOCUMENT_NODES` до `400_000` только в
локальном аудиторском процессе. Для четырёх корней запустите:

```bash
python scripts/reextract_form_roots_issue545.py SOURCE_CF NEW_EXPORT PRIVATE_UUID_LIST
```

Сверяйте целевые UUID и хэши `FORM_ROOT_PROOF` из локального журнала
с отчётами повторно распакованных пар. Журнал содержит приватные
идентификаторы, публикуйте только агрегаты.
