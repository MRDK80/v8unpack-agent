# elem.json и form_elements_index (elem_parser)

После распаковки обычной формы агент видит не только `Form.obj.bsl`, но и
`*.elem.json`. `Form.obj.bsl` содержит обработчики, а `elem.json` — структуру
формы: группы, панели, кнопки, поля, привязки и страницы.

```python
from pathlib import Path
from v8unpack_agent import parse_elem_json

result = parse_elem_json(Path("unpacked/Form/ФормаЭлемента"))

if result.elem_index_ok:
    print(result.elements)
else:
    print(result.warnings)
```

Если `elem_index_ok=False`, основной текстовый слой формы остаётся доступен.
Это не ошибка распаковки, а сигнал о неполноте структурного контекста.

## Нормализованное дерево для elem_sha256

Для вычисления `elem_sha256` (issue #40) хэшируется **нормализованное** дерево
элементов — только структурно значимые поля:

| Поле | Назначение |
|---|---|
| `name` | Имя элемента |
| `type` | Тип элемента (`InputField`, `Button`, …) |
| `path` | Путь в дереве |
| `parent` / `parent_path` | Родительский элемент |
| `page` | Страница формы |
| `source` / `data_path` | Привязка реквизита (см. ниже) |
| `handler` | Обработчик события |

Косметические поля (`left`, `top`, `width`, `height`, `color`, `font`, GUID и
пр.) **исключены** — сдвиг элемента на пиксель или смена цвета не дают
`structure_modified`.

## Граница достоверности

Вложенность **групп** не реконструируется из публичных артефактов — она только
в raw/info-векторах (недокументированный формат платформы). `parse_elem_json`
честно помечает это в `warnings`. Хэш строится по тому, что достоверно:
панели, страницы, плоский список элементов страницы, привязки, обработчики.

## Привязка элемента к данным (data_path)

Поле `data_path` заполняется `parse_elem_json` из секции `data` файла
`*.elem.json`. Механизм зависит от вида формы и выбирается автоматически
по наличию поля `prop` в записях `data` (`is_legacy_form_data`).

### Обычные формы — через `prop`

Источник данных назван в поле `prop` записи, имя реквизита лежит в
`raw[4][1]` при теге `raw[4][0] == "14"`:

| `prop` | Имя реквизита | `data_path` |
|---|---|---|
| `СправочникОбъект` | `Город` | `СправочникОбъект.Город` |
| `ИнформационнаяНадписьАдрес` | совпадает с `prop` | `ИнформационнаяНадписьАдрес` |
| отсутствует | — | привязки нет |

Совпадение имени реквизита с `prop` означает, что элемент связан с
самостоятельным реквизитом формы, а не с реквизитом объекта — префикс в
этом случае не добавляется.

Тег `"14"` **сам по себе привязки не доказывает**: он присутствует у всех
элементов, включая надписи, разделители и панели команд. Признаком служит
только непустой `prop`.

Стандартные реквизиты (`Код`, `Наименование`, `Родитель`) в обычных формах
разрешаются наравне с прочими — привязка идёт по имени, карта UUID не нужна.

### Управляемые формы — через UUID

Поля `prop` нет; привязка задана UUID реквизита объекта-владельца. UUID
разрешается через карту `uuid -> имя реквизита`, построенную из
`Catalog.json` / `Document.json` соседнего объекта метаданных. Карта строится
модулем [`object_decoder`](object_decoder.md) (#84, PR #87) — собственной
реализации обхода `header` у `elem_parser` больше нет. Служебные UUID (самой
формы, элементов оформления) в карте отсутствуют и отсеиваются.

Разбор по UUID к обычным формам **не применяется**: там UUID внутри `raw`
описывают класс виджета, а не привязку, и попытка их разрешить давала
ложные срабатывания (issue #85).

### Структурный fallback управляемых форм

Если явный путь и UUID не дали результата, `parse_elem_json` применяет
консервативный fallback по структуре формы. Он разрешает только два случая:

1. Имя элемента точно совпадает с именем реквизита формы из `props` —
   `data_path` равен этому имени. `props` обходится рекурсивно, поэтому
   учитываются и вложенные реквизиты в `child`/других дочерних контейнерах.
2. Непосредственный родительский сегмент ключа `data` точно совпадает с
   реквизитом формы, а имя элемента начинается с имени родителя — элемент
   считается колонкой таблицы и получает путь
   `<родитель>.<остаток имени>`.

Приоритет источников: явно заданный путь → UUID реквизита → структурный
fallback. Fallback не перебивает уже найденную привязку.

Совпадения по произвольному или «лучшему» префиксу не используются:
`unique_prop_prefix`, `longest_prop_prefix` и остальные неоднозначные случаи
остаются без `data_path`. Это защищает индекс от правдоподобных, но ложных
привязок.

### Элементы без привязки

Отсутствие `data_path` — штатный результат, а не признак неполноты, для
надписей, страниц, групп, разделителей, панелей команд и кнопок.

Если UUID отсутствует, элемент управляемой формы всё ещё может получить
привязку через доказуемый структурный fallback. Если точного реквизита формы
или непосредственного родителя-таблицы нет, `data_path` не создаётся.
Тип реквизита декодируется модулем
[`object_decoder`](object_decoder.md) (#84) и на создание привязок не влияет:
обогащение типом происходит после того, как путь уже подтверждён.

### Сервисные формы: отсутствие `Объект.*` — не пробел парсера

Мастера, помощники и диалоги привязывают поля к временным реквизитам самой
формы, а не к реквизитам объекта метаданных. У формы подбора или помощника
настройки нет объекта, который она редактирует, поэтому путей вида
`Объект.Реквизит` в ней не будет никогда.

Такие формы отделяются модулем
[`form_classifier`](form_classifier.md) (#98, PR #99) и не смешиваются
с объектными при подсчёте агрегированного покрытия. Низкое покрытие
`Объект.*` у формы `ПомощникПодключенияЭДО` — корректный результат разбора,
а не потеря привязок.

### Проверено на реальной выгрузке

`Catalog/Банки`, конфигурация УТ 10.3:

| Форма | Элементов | С привязкой | Warnings |
|---|---|---|---|
| ФормаЭлемента (обычная) | 20 | 8 | 0 |
| ФормаСписка (обычная) | 7 | 4 | 0 |
| ФормаЭлементаУправляемая | 19 | 11 | 0 |

Дополнительный аудит структурного fallback на конкретной реальной выгрузке:

| Метрика | Количество |
|---|---:|
| Исходно неразрешённые Field-записи | 4549 |
| Безопасно разрешены | 3292 |
| — точные реквизиты формы | 1209 |
| — колонки таблиц | 2002 |
| — дополнительные вложенные `props` | 81 |
| Оставлены неразрешёнными | 1257 |
| — `unique_prop_prefix` среди остатка | 520 |
| — `longest_prop_prefix` среди остатка | 23 |
| — прочие `unresolved` | 714 |

Все 81 дополнительно найденный точный реквизит подтверждены во вложенных
узлах `props`. Категории `unique_prop_prefix` и `longest_prop_prefix` не
разрешались. Числа характеризуют эту выгрузку и не являются гарантией
процента покрытия для других конфигураций.

Эта метрика считает только Field-записи и **несопоставима** с общим счётчиком
разрешённых `data_path` по всем элементам формы. Приведение метрик к единой
базе — задача [#90](https://github.com/MRDK80/v8unpack-agent/issues/90).

## Формы с пустым tree

На production-выгрузке (2231 директория форм) 80 форм дают
`elem_index_ok=False` и warning «Элементы формы не найдены»:
`.elem.json` содержит `tree: []`.

Это **известное ограничение парсера**, а не свойство самих форм. Все
затронутые формы — обычные (неуправляемые); их разметка хранится в бинарном
виде и текущей реализацией не читается. Управляемые формы обрабатываются
корректно.

### Приоритет: 10 форм со стандартными объектными именами

Три `ФормаЗаписи` регистров сведений — гарантированно объектные, форма записи
регистра содержит поля измерений и ресурсов:

```
InformationRegister/АдресныйКлассификатор/InformationRegisterForm/ФормаЗаписи
InformationRegister/ОтветственныеЛица/InformationRegisterForm/ФормаЗаписи
InformationRegister/ПаспортныеДанныеФизЛиц/InformationRegisterForm/ФормаЗаписи
```

Семь основных форм `Форма` отчётов и обработок: `КонсольОтчетов`,
`ПроведениеДокументовПоРегистрамНДС`, `УдалениеПисемЭлектроннойПочты`,
`ЭкспортИмпортКонтактныхДанныхОбъектов`, `АнализРезультатовАнкетирования`,
`АнализЦен`, `Диаграмма`.

### Остальные 70 форм

Среди них 14 форм настроек отчётов (`ФормаНастройки`, `ФормаНастройка`).
Это полноценные формы с полями данных — показатели, группировки строк и
колонок, отборы, период, — а не диалоги подтверждения.

### Как это отражается в метрике

Формы с пустым `tree` получают `form_class="unknown"` и **исключаются из
знаменателя** метрики покрытия: они не занижают процент, но и не попадают
в числитель. Причина фиксируется машиночитаемым кодом
(`platform_object_name_unparsed`, `empty_tree_name_hint`) — см.
[`form_classifier`](form_classifier.md).

Отнесение таких форм к сервисным было бы ошибкой: объектные формы исчезли бы
из метрики, а отчёт показал бы благополучные цифры при нечитаемой разметке.

## Схлопывание одноимённых записей

Один элемент может прийти в индекс из двух секций: из `data` — с привязкой
и позицией в дереве, из `props` — как реквизит формы. В формах списка имена
совпадают (`СправочникСписок` — и реквизит, и таблица), из-за чего поиск
элемента по имени становился неоднозначным.

Такие записи схлопываются в одну, приоритет у `data`. Список слитых
источников сохраняется в поле `merged_sources`. Не сливаются:

- реквизиты формы, которым не соответствует ни один элемент
  (`СправочникОбъект`) — остаются записями с `source="props"`;
- элементы с разными непустыми `path` — это разные элементы с одинаковым
  именем в разных группах.

## forms_index и forms_scan_index

`forms_index` (FormsIndex) — **карта актуальности** для pipeline-шага
распаковки. Содержит:

| Поле | Тип | Значение |
|---|---|---|
| `bin_path` | string | Путь к исходному `Form.bin` |
| `unpacked_root` | string | Директория с распакованными текстами |
| `bin_mtime` | float | Unix-время изменения `Form.bin` при распаковке |
| `unpacked_mtime` | float | Unix-время последней распаковки; `bin_mtime > unpacked_mtime` → форма устарела |
| `extraction_ok` | bool | `true` — полная распаковка |
| `warnings` | array | Диагностика при частичной распаковке |

Этот индекс не является источником истины и не содержит содержимого `Form.bin`,
строк подключения или имён баз — его безопасно коммитить в репозиторий.
