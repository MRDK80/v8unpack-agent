# form_classifier — объектные и сервисные формы

Модуль отделяет **объектные** формы от **сервисных**, чтобы агрегированная
метрика покрытия `data_path` не занижалась архитектурным паттерном
платформы.

Это каноническое место двух контрактов: классификации форм и метрики
покрытия `data_path`. Метрика не сериализуется в post-run report, поэтому
отдельного документа для неё нет.

Issue [#98](https://github.com/MRDK80/v8unpack-agent/issues/98),
PR [#99](https://github.com/MRDK80/v8unpack-agent/pull/99).

## Зачем

Метрика покрытия `data_path` (issue #90) считает долю полей формы, привязанных
к данным. На реальной выгрузке она давала заниженный результат, и первое
объяснение звучало как «парсер не дорабатывает».

Объяснение оказалось неверным. Формы-мастера, помощники и диалоги привязывают
поля не к реквизитам объекта метаданных (`Объект.Реквизит`), а к **временным
реквизитам самой формы**. Это штатный приём платформы: у формы подбора или
помощника настройки нет объекта, который она редактирует. Считать такую
форму непокрытой — ошибка метрики, а не дефект кода.

`form_classifier` вводит явное разделение, и покрытие считается отдельно
по каждому классу.

## Классы форм

| Класс | Значение | Когда присваивается |
|---|---|---|
| `FormClass.OBJECT` | `"object"` | Хотя бы один `data_path` начинается с `Объект.` |
| `FormClass.SERVICE` | `"service"` | Имя из списка сервисных паттернов, либо data-элементы есть, но ни одной привязки `Объект.*`, либо data-элементов нет вовсе |
| `FormClass.UNKNOWN` | `"unknown"` | Элементы формы не извлечены из `.elem.json` |

`FormClass` наследуется от `str`, поэтому сериализуется напрямую и сравнивается
как со строкой, так и с константой:

```python
form_class == "service"            # True
form_class == FormClass.SERVICE    # True
```

## API

### classify_form

Основная точка входа. Объединяет два критерия по OR.

```python
from v8unpack_agent.form_classifier import classify_form

form_class = classify_form(
    form_name="ПомощникНастройки",
    elements=result.elements,
)
# FormClass.SERVICE
```

Порядок проверок:

1. Пустой список элементов → `UNKNOWN` (сразу, без дальнейших проверок).
2. Имя совпало с сервисным паттерном → `SERVICE`.
3. Структура привязок дала `SERVICE` → `SERVICE`.
4. Структура привязок дала `OBJECT` → `OBJECT`.

Достаточно одного сервисного признака. Обратное неверно: наличие `Объект.*`
не перекрывает совпадение по имени — форма `ПодборПозиций` остаётся
сервисной, даже если часть её полей привязана к объекту.

### classify_form_by_name

Проверяет только имя. Возвращает `SERVICE` при совпадении префикса
(регистронезависимо), иначе `UNKNOWN` — «данных недостаточно», а не «объектная».

```python
classify_form_by_name("МастерЗаполнения")   # FormClass.SERVICE
classify_form_by_name("ФормаЭлемента")      # FormClass.UNKNOWN
```

### classify_form_by_bindings

Проверяет только структуру. Учитывает элементы типов из `DATA_ELEMENT_TYPES`
(`Field`, `InputField`, `Table`, `CheckBox`, `Calendar`, `Chart`, `Picture`);
`Label`, `Group`, `Button` и прочие служебные игнорируются.

```python
classify_form_by_bindings([
    {"type": "Field", "data_path": "Объект.Наименование"},
])                                          # FormClass.OBJECT

classify_form_by_bindings([
    {"type": "Field", "data_path": "ТекущийШаг"},
])                                          # FormClass.SERVICE

classify_form_by_bindings([
    {"type": "Label", "data_path": None},
])                                          # FormClass.SERVICE
```

Последний случай — форма без полей данных вообще. Это информационная или
навигационная форма, по архитектуре сервисная. `UNKNOWN` здесь не возвращается:
элементы есть, парсер отработал, просто привязок нет.

### classify_empty_tree_form

Отдельная функция для форм, у которых `.elem.json` содержит `tree: []`.
Возвращает пару «класс, машиночитаемая причина».

```python
from v8unpack_agent.form_classifier import classify_empty_tree_form

classify_empty_tree_form("ДиалогПодтверждения")
# (FormClass.SERVICE, "by_service_pattern")

classify_empty_tree_form("ФормаЗаписи")
# (FormClass.UNKNOWN, "platform_object_name_unparsed")

classify_empty_tree_form("ФормаНастройки")
# (FormClass.UNKNOWN, "empty_tree_name_hint")
```

| Причина | Класс | Смысл |
|---|---|---|
| `by_service_pattern` | `service` | Совпадение с проверенным списком — единственный случай, когда класс присваивается без разметки |
| `platform_object_name_unparsed` | `unknown` | Стандартное имя объектной формы платформы; сигнал о пробеле в `elem_parser` |
| `empty_tree_name_hint` | `unknown` | Имя похоже на сервисное, подтверждения нет |
| `unparsed_empty_tree` | `unknown` | Имя не распознано, разметки нет |
| `no_name` | `unknown` | Имя формы не передано |

### classify_no_widgets_form

Точка входа для форм категории `NO_TABULAR_NO_WIDGETS` (#109).
Принимает `form_name` и `reason`; возвращает `FormClass`.

```python
from v8unpack_agent.form_classifier import classify_no_widgets_form
from v8unpack_agent.elem_parser import UnindexedReason

fc = classify_no_widgets_form(
    form_name="ФормаПечати",
    reason=UnindexedReason.NO_TABULAR_NO_WIDGETS,
)
# FormClass.SERVICE
```

Оба условия обязательны:

1. `reason == UnindexedReason.NO_TABULAR_NO_WIDGETS`.
2. `classify_empty_tree_form(form_name)` даёт `by_service_pattern` или
   `empty_tree_name_hint`.

Возвращает `UNKNOWN`, если причина другая, имя пустое, либо имя даёт
`platform_object_name_unparsed` или `unparsed_empty_tree`.

`classify_form` и `classify_empty_tree_form` при этом не изменялись.

## Метрика покрытия data_path

Каноническое описание `calc_data_path_coverage()` и `CoverageReport`. Метрика
считается поверх классификации и потому живёт в этом документе.

В знаменатель входят только элементы из `DATA_ELEMENT_TYPES`. Служебные
элементы оформления не учитываются ни в числителе, ни в знаменателе.

Поле `form_class` заполняется автоматически:

```python
from v8unpack_agent.coverage_metric import calc_data_path_coverage

report = calc_data_path_coverage(result.elements, form_name="ФормаЭлемента")
report.form_class    # "object"
report.coverage_pct  # доля привязанных data-элементов
report.to_dict()     # {"...": ..., "form_class": "object"}
```

Без параметра `form_name` классификация идёт только по структуре привязок —
обратная совместимость со старым кодом сохранена.

Обёртка `calc_coverage_from_elem_index` при `elem_index_ok=False` или пустых
элементах вызывает `classify_empty_tree_form` и возвращает нулевой отчёт
с соответствующим классом.

`CoverageReport` в post-run report не сериализуется: модель отчёта описана
в [`run_report`](run_report.md) и полей покрытия не содержит.

### Циклический импорт

`form_classifier` импортирует `DATA_ELEMENT_TYPES` из `coverage_metric`
на уровне модуля. Обратное направление реализовано **ленивым импортом
внутри функций**:

```python
def calc_data_path_coverage(elements, form_name=None):
    from v8unpack_agent.form_classifier import classify_form  # noqa: PLC0415
```

Импорт `form_classifier` на верхнем уровне `coverage_metric` ломает загрузку
всего пакета.

## Почему пустой tree не даёт SERVICE

Промежуточный вариант реализации трактовал пустой `tree` как «безопасный
дефолт»: раз элементов нет, объектной форма быть не может. Рассуждение
выглядело правдоподобно и было опровергнуто верификацией на исследованном
корпусе.

Среди форм с пустым `tree` обнаружились:

- три формы записи регистров сведений — такая форма содержит поля измерений
  и ресурсов, это объектная форма по определению;
- семь основных форм отчётов и обработок;
- четырнадцать форм настроек отчётов — полноценные формы с показателями,
  группировками и отборами, а не диалоги.

Отнесение их к `SERVICE` вычеркнуло бы объектные формы из знаменателя метрики
и **скрыло бы реальный пробел в парсере**: отчёт показал бы благополучные
цифры при нечитаемой разметке.

Принцип: классификатор не придумывает класс, когда парсер не предоставил
структуру формы. `unknown` — честный результат, `service` — догадка.

## Константы

### SERVICE_FORM_NAME_PATTERNS

Шестнадцать префиксов, проверенных на исследованном корпусе: `помощник`,
`мастер`, `диалог`, `добавление`, `управление`, `регистрация`, `программа`,
`подбор`, `подсказка`, `предопределен`, `включение`, `обновление`,
`конвертация`, `реклама`, `нерекомендуем`, `вопрос`.

**Не добавляйте сюда широкие префиксы.** Под `форма` попадают стандартные
объектные формы платформы: `ФормаЭлемента`, `ФормаДокумента`, `ФормаЗаписи`,
`ФормаСписка`. Один такой префикс переведёт сотни объектных форм в `service`
и обнулит смысл метрики.

Префикс `черновик` был удалён из списка: формы вида `ЧерновикДокумента`
содержат привязки `Объект.*`, классификация делегируется структурному
критерию.

### PLATFORM_OBJECT_FORM_NAMES

Семнадцать стандартных имён объектных форм платформы для **точного**
совпадения: `форма`, `формаобъекта`, `формаэлемента`, `формадокумента`,
`формагруппы`, `формасписка`, `формавыбора`, `формавыборагруппы`,
`формазаписи`, `формаконстант`, `формаотчета`, `формаотчёта`,
`формаостатков`, `формадвижений`, `формарегистра`, `формажурнала`,
`формануля`.

Используется только в `classify_empty_tree_form` — как диагностический
маркер, требующий внимания к парсеру.

### EMPTY_TREE_NAME_HINTS

Девятнадцать префиксов, которые *выглядят* сервисными, но не подтверждены
проверкой. Влияют **только на код причины**, не на класс формы. Расширение
этого списка безопасно: оно уточняет диагностику, но никогда не меняет
результат классификации.

## Верификация

Проверка выполняется на реальной выгрузке локально: скрипты
`verify_*` не входят в репозиторий, поскольку требуют данных, которых нет
в открытом доступе. Результат прикладывается к PR текстом.

Датированный результат локального прогона на корпусе A на момент #98:

```text
Найдено директорий форм: 2231

Всего форм обработано: 2037
  object:                 164
  service:                1793
    из них empty_tree:      0
  unknown:                 80
    из них empty_tree:     80
  platform_auto (ok):     194
  ошибок/пропущено:         0
  итого директорий:      2231

Empty-tree формы (80) — причины классификации:
    70x  empty_tree_name_hint
    10x  platform_object_name_unparsed  ← ПРОВЕРИТЬ ПАРСЕР

Баланс директорий соблюдён: 2231 из 2231.
```

Актуальные агрегаты по доле неиндексированных форм зафиксированы в
[исследовании по #229](research/unindexed_share_issue229.md). Цифры выше —
исторический снимок, они не обновляются задним числом.

Ключевые инварианты, которые обязана подтвердить верификация:

- `service` с `empty_tree` = 0 — ни одна форма не признана сервисной без разметки;
- баланс: `object + service + unknown + platform_auto + errors` = число
  директорий;
- сервисные формы с `Объект.*` в путях выводятся отдельно как потенциальные
  ложноположительные (шесть форм подбора — совпадение по имени осознанное).

## Связь с диагностикой неиндексируемых форм (#105)

Формы с пустым `tree`, которые не подняли fallback #100 и #103, получают
`form_class="unknown"` и исключаются из знаменателя метрики покрытия.
Начиная с #105 у каждой такой формы есть машиночитаемая причина —
`elem_parser.classify_unindexed_form()` возвращает `UnindexedReason`
(см. [`elem_parser`](elem_parser.md)).

Датированное распределение на корпусе A на момент #105:

| Категория | Форм | Состояние |
|---|---:|---|
| без виджетов данных (`NO_TABULAR_NO_WIDGETS`) | 17 | переведены в `service` в #109 (PR #111) |
| непопадающие UUID колонок `TabularField` | 26 | исправлены в #107 (PR #110) |
| пустая карта реквизитов владельца (`CommonForm`) | 2 | диагноз `NO_OWNER_OBJECT` by design (#108) |

Перевод форм категории `NO_TABULAR_NO_WIDGETS` из `unknown` в `service`
реализован через `classify_no_widgets_form()`. `classify_empty_tree_form()`
не расширялась: `SERVICE` по-прежнему выдаётся только при совпадении
с проверенным `SERVICE_FORM_NAME_PATTERNS`.

Результат на момент #109: 17 из 17 форм → `SERVICE`, ни одного ложного
`SERVICE`, ни одного исключения.

## Ограничения

Восемьдесят форм датированного прогона оставались в `unknown`. Все они —
**обычные** (неуправляемые) формы, разметка которых хранится в бинарном
виде и не читается текущим `elem_parser`. Управляемые формы парсятся
корректно.

Приоритет к устранению — десять форм с причиной
`platform_object_name_unparsed`, из них три формы записи регистров сведений
гарантированно объектные и напрямую занижают покрытие.

Классификатор эту проблему не решает и не должен: его задача — не скрыть её.
