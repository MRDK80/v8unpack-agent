# object_decoder — реквизиты объекта из raw-секции `header`

Модуль читает raw-секцию `header` из объектных JSON выгрузки v8unpack
(`Catalog.json`, `Document.json` и аналогичных) и возвращает нормализованную
структуру реквизитов и табличных частей.

Задача решает issue #84 (PR #87).

## Зачем это нужно

`v8unpack` сохраняет свойства объектов метаданных в частично декодированном
виде: имена, UUID и типы реквизитов лежат внутри вложенных списков `header`,
но читаемых секций `Properties` или `Attributes` в JSON нет.

Без этого модуля `catalog_resolver` знал имя реквизита из `data_path`, но не
мог получить его тип. `elem_parser` при этом строил UUID-карту собственной
рекурсивной реализацией, дублируя логику обхода.

## Публичный API

```python
from pathlib import Path
from v8unpack_agent.object_decoder import decode_object_attributes

result = decode_object_attributes(Path("cf_export/Catalog/Банки/Catalog.json"))

if result.ok:
    for prop in result.data["Properties"]:
        print(prop["Name"], prop["Type"])
```

### `decode_object_attributes(object_json: Path) -> DecodeResult`

Единственная публичная функция. Принимает путь к объектному JSON, возвращает
`DecodeResult`.

### `DecodeResult`

| Поле | Тип | Описание |
|---|---|---|
| `ok` | `bool` | Успешность декодирования |
| `data` | `dict` | `{"Properties": [...], "TabularSections": [...]}` |
| `error` | `DecodeError \| None` | Причина отказа при `ok=False` |
| `warnings` | `list[str]` | Диагностика повреждённых узлов |

### `DecodeError`

| Значение | Когда возникает |
|---|---|
| `JSON_NOT_FOUND` | Файл не существует |
| `JSON_PARSE_ERROR` | Файл не читается как JSON |
| `HEADER_MISSING` | В JSON отсутствует ключ `header` |
| `VERSION_UNSUPPORTED` | `header` не является списком |

При любой ошибке `data` содержит пустые списки — вызывающий код не обязан
проверять наличие ключей.

## Формат результата

```json
{
  "Properties": [
    {"UUID": "a1b2...", "Name": "ИНН", "Type": "String", "Synonym": "ИНН"},
    {"UUID": "c3d4...", "Name": "Регион", "Type": "Ref#df7ce7e5-...", "Synonym": null}
  ],
  "TabularSections": [
    {
      "UUID": "e5f6...",
      "Name": "ВидыДеятельности",
      "Synonym": null,
      "Properties": [
        {"UUID": "0a1b...", "Name": "ВидДеятельности", "Type": "Ref#aee2d03d-...", "Synonym": null}
      ]
    }
  ]
}
```

Структура совместима с `catalog_resolver.resolve_data_path` без изменения
его публичного API.

## Резолюция типов

Примитивные типы разрешаются в читаемое имя:

| Значение `Type` | Смысл |
|---|---|
| `String` | Строка |
| `Number` | Число |
| `Boolean` | Булево |
| `Date` | Дата |
| `Ref#<uuid>` | Ссылка на объект метаданных, UUID цели |
| `None` | Тип не определён для данного layout |

Ссылочные типы намеренно остаются в виде `Ref#<uuid>`: приведение UUID к
имени объекта (`CatalogRef.Контрагенты`, `EnumRef.ЮрФизЛицо`) требует
глобального индекса всех объектов выгрузки и вынесено в issue #88.

## Поддерживаемые layout

Модуль пробует три стратегии по убыванию точности.

1. **Production-layout** (`_decode_real_header`) — строковые теги, раздельные
   контейнеры реквизитов и табличных частей. Поиск идёт по устойчивой
   структуре wrapper/descriptor, а не по фиксированным индексам, поскольку
   позиции контейнеров различаются между `Catalog`, `Document` и версиями
   платформы.
2. **Compact owner-metadata** (`_decode_compact_attribute_wrapper`) —
   верхнеуровневые реквизиты в `header[0][6]`, отличается наличием поля
   locale. Тип в этом layout недоступен, реквизиты получают `Type=None`.
3. **Legacy walker** (`_walk_node`) — рекурсивный обход с целочисленными
   тегами, ограничение глубины 20 уровней. Используется как fallback для
   старого нормализованного формата.

Табличные части распознаются по связке «header-wrapper + флаг + counted-контейнер
колонок». Их UUID и UUID их колонок исключаются из списка верхнеуровневых
реквизитов, чтобы один узел не попал в результат дважды.

## Best-effort поведение

Модуль не бросает исключений при повреждённых данных. Нераспознанный узел
пропускается с записью в `warnings`, остальные декодируются. Это позволяет
построить индекс форм даже для конфигураций с неизвестной версией
сериализации.

Если ни одна стратегия не дала ни одного реквизита, возвращается `ok=True`
с пустыми списками — отсутствие реквизитов у объекта является нормой
(например, для регистров без измерений).

## Связь с elem_parser

`elem_parser.load_owner_attribute_map()` строит UUID-карту из результата
этого модуля. Собственная рекурсивная реализация обхода `header` удалена
в #84: прежний код собирал UUID из произвольных узлов и на четырёх legacy-формах
давал мусорную карту из одной записи, которая никогда не использовалась.

Карта применяется только к управляемым формам. Обычные формы декодируют
привязку через поле `prop` (см. `_decode_legacy_data_path`), и UUID-резолюция
для них не выполняется.

## Результаты на production-выгрузке

Прогон на 6551 объекте метаданных, 15888 реквизитов:

| Категория | Кол-во | Доля |
|---|---:|---:|
| Примитивы | 7457 | 46.9% |
| `Ref#uuid` | 5226 | 32.9% |
| `Type=None` | 3205 | 20.2% |

- Нераспознанных кодов типа: 0.
- Ошибок декодирования: 0.

Остаток `Type=None` — compact-layout и составные типы (`CompositeType`),
намеренно не разбираемые в #84.

Пример на `Catalog/Банки`: 11 из 11 реквизитов типизировано, 0 warnings.
Пример на `Catalog/Контрагенты`: 31 из 31, включая две табличные части.

## Известные ограничения

- Длина строкового реквизита и его квалификаторы не декодируются — в
  исследованных layout эти данные не обнаружены на устойчивой позиции.
- `Synonym` заполняется не всегда: в production-layout он присутствует, в
  compact — часто отсутствует.
- Составные типы (`CompositeType`) дают `Type=None`; разбор списка допустимых
  типов не реализован.
- Приведение `Ref#<uuid>` к имени объекта метаданных — issue #88.
