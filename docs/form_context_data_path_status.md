# Явное отрицательное знание о data_path: form_context

Issue #141. Модуль `v8unpack_agent/form_context.py`. Дополняет
[form_context.md](form_context.md).

## Зачем

Недоказанная привязка `data_path` не угадывается. До #141 такое значение
просто отсутствовало в `## SUMMARY`, а объяснение жило только в свободном
тексте `warnings`. Если `warnings` исключены из контекста или обрезаны
бюджетом, модель видела пропуск без объяснения. Теперь отрицательный факт
передаётся явно, машинно-читаемо и не зависит от разбора `warnings`.

## Каноническая структура

`FormContext.unresolved_data_paths: list[dict]` — по записи на каждую
недоказанную привязку. Поле добавлено со значением по умолчанию `[]`, поэтому
существующие вызовы конструктора `FormContext(...)` не меняются.

```json
{
  "scope": "form",
  "element": null,
  "data_path": null,
  "status": "unknown_layout",
  "reason": "layout_not_recognized"
}
```

| Ключ | Значение |
|------|----------|
| `scope` | `"form"` — структура формы не прочитана целиком; `"element"` — конкретный элемент данных |
| `element` | имя элемента для `scope == "element"`, иначе `null` |
| `data_path` | всегда `null`: тип поля сохраняется, строковый маркер сюда не попадает |
| `status` | статус из конечного набора, см. ниже |
| `reason` | стабильный код причины, см. ниже |

Доказанные привязки сюда не попадают: они по-прежнему живут в
`summary.relations` (`kind == "data"`) и в `resolved_relations`, их формат и
смысл не изменились.

## Статусы

| `status` | Семантика |
|----------|-----------|
| `unresolved` | привязка не доказана; конкретная причина — в `reason` |
| `unknown_layout` | файл структуры формы есть и является JSON, но его раскладка не распознана парсером |
| `not_found` | отсутствие целевой сущности доказано |

`not_found` зарезервирован. Ни одна текущая диагностическая ветка не
доказывает отсутствие целевой сущности: пустой результат парсера или
резолвера — это отсутствие доказательства, а не доказательство отсутствия.
Поэтому модуль `not_found` не выдаёт. Классификация ссылочных UUID (#143) на
`data_path` не переносится.

## Коды причин

| `reason` | `status` | Структурный признак |
|----------|----------|---------------------|
| `form_dir_missing` | `unresolved` | каталога формы нет на диске |
| `elem_json_missing` | `unresolved` | каталог есть, локатор `parse_elem_json` не нашёл файл структуры |
| `elem_json_invalid` | `unresolved` | файл структуры найден, но не читается как JSON |
| `layout_not_recognized` | `unknown_layout` | файл — корректный JSON, но `parse_elem_json` вернул `elem_index_ok=False` |
| `binding_not_proven` | `unresolved` | структура прочитана, элемент данных есть, а доказанной привязки у него нет |

Причины определяются по структурным фактам — каталог, файл, флаг
`elem_index_ok`, список привязок, — а не по тексту `warnings`. Разные причины не
сводятся к одному коду. Для `binding_not_proven` учитываются только типы из
`coverage_metric.DATA_ELEMENT_TYPES`: у служебных элементов (`Label`, `Group`
и т. п.) привязки нет по определению. Порядок записей повторяет
`summary.elements`, дубликаты имён схлопываются; результат детерминирован.

Проверка `json.loads` для `elem_json_invalid` только различает «не JSON» и
«JSON с нераспознанной раскладкой». Второго пути разбора структуры она не
вводит.

## LLM-проекция

В `to_llm_prompt_fragment()` каждая запись выводится отдельной строкой в
секции `## SUMMARY` сразу после JSON выжимки:

```text
data_path: "<UNKNOWN_LAYOUT: путь не доказан>"; status: unknown_layout; reason: layout_not_recognized; scope: form
data_path: "<UNRESOLVED: путь не доказан>"; status: unresolved; reason: binding_not_proven; scope: element; element: "ПолеФормы"
```

| `status` | Маркер |
|----------|--------|
| `unresolved` | `<UNRESOLVED: путь не доказан>` |
| `unknown_layout` | `<UNKNOWN_LAYOUT: путь не доказан>` |
| `not_found` | `<NOT_FOUND: отсутствие доказано>` |

Гарантии:

- `null` не является единственным сигналом: маркер виден прямо в значении;
- строка начинается с `data_path: `, маркер идёт первым, статус и причина —
  в той же строке;
- строка атомарна относительно `max_chars`: если лимит попадает внутрь неё,
  строка отбрасывается целиком, поэтому маркер не остаётся без статуса;
- `len(result) <= max_chars` при положительном лимите сохраняется,
  `max_chars=-1` по-прежнему отключает обрезку;
- порядок секций `# FORM` → `## SUMMARY` → `## OBJECT_ATTRIBUTES` → `## BSL`
  не меняется;
- без недоказанных привязок фрагмент совпадает с прежним форматом;
- неизвестный статус в записи, собранной вручную, выводится fail-closed
  маркером `unresolved`.

Строковый маркер относится только к LLM-проекции. В канонической
структуре `data_path` остаётся `null`.

## Ограничения

- `warnings` сохраняются как дополнительная диагностика и не удаляются.
- Токенный бюджет (#125) должен считать строку отрицательного знания
  атомарной так же, как это делает символьный лимит.
- Угадывание `data_path`, расширение эвристик разбора и изменение резолвера
  `Ref#uuid` в scope не входят.
