# Общий смысловой индекс и снимок (#325)

Модуль `v8unpack_agent.search_index` строит провайдер-независимый индекс над
`FragmentationResult` (#324), сохраняет его снимком и проверяет совместимость
и свежесть. Эмбеддер передаётся явно; сеть, ChromaDB и автоматическая
пересборка не используются. Контракты `search_contract/1`, `search_corpus/1`
и `search_fragments/1` не меняются.

## API

- `EmbedderIdentity(name, version, dimension, config_hash)` задаётся вызывающей
  стороной; `config_hash` — непрозрачная строка.
- `build_index(result, embedder)` — полная пересборка. Вектор отклоняется при
  неверной размерности, `NaN`, бесконечности, `bool`, нулевом векторе или
  неверном числе векторов (`SearchIndexError`, код `invalid_vector`); сбой
  эмбеддера даёт `embedder_failed` без текста исходного исключения.
- `save_index(index, path, *, schema="search_index/1")` — атомарная
  публикация; возвращает схему записанного снимка. Формат `search_index/1` —
  один JSON-файл: временный файл рядом и одна замена `os.replace`, при сбое
  прежний снимок остаётся без изменений. Формат `search_index/2` — см.
  «Формат хранения search_index/2 (#413)».
- `load_index(path)` — читает оба формата по полю `schema`; проверка
  структуры, контрольных сумм и каждого вектора; повреждение даёт
  `SearchIndexError("corrupt_snapshot")`.
- `query_index(index, query, embedder, fragmentation=None)` — выдача по
  артефактам (#362): каждый артефакт встречается не более одного раза. Порядок
  отбора:
  1. фильтры запроса применяются к каждой записи индекса;
  2. для каждого артефакта остаётся лучший фрагмент — наибольшая оценка, при
     равенстве меньший `document_id`;
  3. отбираются до `top_k` разных артефактов по убыванию оценки, при
     равенстве — по `document_id` лучшего фрагмента.

  `top_k` отсчитывается после устранения повторов: при достаточном числе
  артефактов, прошедших фильтры, попаданий ровно `top_k`, иначе — по числу
  таких артефактов. Попадание указывает `document_id` и оценку лучшего
  фрагмента. Итоговый порядок попаданий в `SearchResult` задаёт контракт
  `search_contract/1`. Точное разрешение, неоднозначность, смысловой fallback
  и объединение точного и смыслового путей — в `search_dispatch` (#326,
  [`search_dispatch.md`](search_dispatch.md)).

## Два уровня (#407)

`object_level(fragmentation)` — уровень объектов: первый фрагмент каждого
артефакта, те же `items` и версия представления; строится один раз на
результат фрагментации. `query_two_level(fragment_index, object_index, query,
embedder, fragmentation)` сливает ранги артефактов двух уровней (RRF, k = 60,
глубина `max(5·top_k, 50)`), запрос векторизуется один раз; диспетчер
применяет его только при `fusion=True` (#423); подробности —
[search_local_model](search_local_model.md).

## Формат хранения search_index/2 (#413)

Решение владельца по итогам #399: векторы — отдельным двоичным файлом,
описания артефактов — общим словарём. `search_index/2` — формат хранения той
же модели индекса: загруженный индекс равен индексу из `search_index/1`
(`SearchIndex.schema` в памяти — `search_index/1`), `assess`, свежесть и
выдача `query_index` не меняются. По умолчанию пишется `search_index/1`;
`/2` выбирается явно: `save_index(..., schema="search_index/2")`,
`build_search_snapshot(..., schema=...)`, `search_cli build --snapshot-format 2`.

Файлы по пути `PATH`:

- `PATH` — метаданные JSON с контрольной суммой: схемы,
  `representation_version`, `EmbedderIdentity`, `artifacts` (уникальные
  описания артефактов), `entries` (записи без векторов, `artifact` — номер в
  словаре) и `vectors: {file, dtype, byteorder, shape, sha256}`;
- `PATH.<sha256[:16]>.vec` — векторы подряд, C-порядок, little-endian,
  форма `(число записей, размерность)`.

Тип векторов выбирается без потерь: `float32`, если каждое значение точно
представимо в float32 (векторы моделей эмбеддингов), иначе `float64`
(например, `hashed-bow-demo`). Поэтому выдача по `/1` и `/2` одного индекса
совпадает побитово. Для `hashed-bow-demo` файл `/2` может быть больше `/1`:
выигрыш формата — для float32-векторов моделей (на синтетике 20 тыс. × 1024:
448 → 90 МБ, загрузка 31 → 3,9 с).

Публикация: сначала атомарно записывается файл векторов (имя по содержимому),
затем одной заменой — метаданные, затем удаляются прежние файлы векторов этого
пути (в том числе при записи `/1` поверх `/2`). При сбое на любом шаге прежний
снимок остаётся читаемым, новый файл векторов удаляется.

Проверки при загрузке: структура и контрольная сумма метаданных, имя файла
векторов (только `<имя PATH>.<16 hex>.vec` в том же каталоге, совпадающее с
`sha256`), sha256 и размер файла векторов, `dtype`/`byteorder`/`shape`,
конечность и ненулевые векторы, номер артефакта, ключи записей, дубликаты
`document_id` — иначе `corrupt_snapshot`. С numpy векторы читаются матрицей
и сразу дают подготовленную матрицу #406; без numpy — модулем `array`
стандартной библиотеки с той же проверкой каждого вектора.

## Производительность (#406)

Индекс и результат фрагментации неизменяемы, поэтому повторные запросы не
повторяют подготовку:

- сигнатура свежести корпуса (три хэша и состав `document_id`) строится один
  раз на `FragmentationResult` через `derived()` (#397);
- `SearchIndex.assess` для той же идентичности эмбеддера и того же объекта
  фрагментации возвращает прежний итог; диспетчер и `query_index` больше не
  считают его дважды;
- при установленном numpy (extra `fast`: `pip install "v8unpack-agent[fast]"`)
  векторы индекса один раз собираются в матрицу float32. Запрос считает
  приближённые оценки одним умножением и отбирает кандидатов: порог — оценка
  `top_k`-го артефакта по лучшему фрагменту минус запас `1e-4`, заведомо
  больший погрешности float32. Оценки кандидатов, выбор лучшего фрагмента и
  порядок считаются прежним кодом, поэтому выдача, оценки, равенства по
  `document_id`, фильтры и `top_k` совпадают с путём без numpy побитово.

Без numpy работает прежний поэлементный путь. Производные значения хранятся
в приватном поле `SearchIndex._cache`: они не входят в равенство, `repr`,
`to_json()` и снимок, формат `search_index/1` не меняется. Матрица занимает
`4 × число фрагментов × размерность` байт (≈66 МБ на 67 тыс. × 256).

## Политика хранения

Исходный текст и поисковое представление в снимке не хранятся (в обоих
форматах). Запись содержит
`document_id`, артефакт, процедуру, координаты, три хэша (`text_sha256`,
`search_sha256`, `source_sha256`) и вектор. Снимок хранит `representation_version`
из `FragmentationResult`, схему корпуса `search_corpus/1`, схему снимка
`search_index/1` и идентичность эмбеддера.

## Статусы

Совместимость и свежесть — две независимые оси (`SearchIndex.assess`).

| Ось | Значения | Что сверяется |
|---|---|---|
| Совместимость | `compatible`, `incompatible` | схемы, `EmbedderIdentity`, `representation_version` (если передан корпус) |
| Свежесть | `fresh`, `stale`, `unverified` | три хэша и состав `document_id` с переданным корпусом |

Без корпуса свежесть — `unverified`: запросы допустимы, статус не выдаётся за
доказанную свежесть. `incompatible` и `stale` блокируют запросы: результат со
статусом `error` и кодом `incompatible_index`. Пересборка — только явным
вызовом `build_index`.
